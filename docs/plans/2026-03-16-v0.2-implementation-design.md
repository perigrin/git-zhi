# v0.2 Implementation Design

v0.2 scales git-zhi from a solo developer's task scheduler to a small-team system — one or two developers alongside one or two coding agents. It adds quality gates, parallelization analysis, regression verification, engineering metrics, documentation health monitoring, and an intelligence layer that decomposes PRDs into executable chains.

## Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Repo layout | Monorepo — all Go binaries under `cmd/` | Shared internal packages, single test suite, single CI pipeline |
| Crochet location | Separate repo (`github.com/perigrin/crochet`) | Claude Code plugin, not a Go binary — different artifact type and release cadence |
| Plugin architecture | `git-zhi-*` binaries on `$PATH` | Git's own subcommand discovery; no registration or config required |
| Phase sequencing | PRD order (phases 1–9) | Natural dependency flow: data model first, then gates, then consumers |
| Schema versioning | Stay at version 1 | v0.2 additions are backward-compatible; v0.1 tools ignore unknown fields |
| VADER sentiment | Go VADER library | Deterministic lexicon-based analysis; no LLM dependency for metrics |
| LSP integration | JSON-RPC client against configured servers | One protocol, all languages; reuses servers developers already have |
| LSP testing | gopls against real test repos | No mocks; gopls ships with the Go toolchain |
| Milestone gate degradation | Skip gates for missing plugins with warning | Allows incremental adoption: core alone, core + verify, full stack |

## Monorepo Layout

```
cmd/
  git-zhi/              # existing core binary
  git-zhi-verify/       # regression verification plugin
  git-zhi-sanbao/       # observatory plugin
  git-zhi-docs/         # documentation health plugin

internal/
  cli/                  # existing — gains milestone lifecycle, --ready, --actor, --workers
  storage/              # existing — unchanged
  issue/                # existing — gains Steps, AC subsections, urgency, reopened, transitions, observed_paths
  milestone/            # existing — gains body, state, resolution, completed timestamp
  graph/                # existing — gains path overlap, parallel assignment, per-actor HEAD
  telemetry/            # existing — gains forecast accuracy, parallel efficiency
  config/               # existing — unchanged
  resolve/              # existing — unchanged
  uuids/                # existing — unchanged
  version/              # existing — unchanged
  updater/              # existing — unchanged
  download/             # existing — unchanged
  verify/               # AC command parser, executor, prioritized ordering
  sanbao/               # DORA, SPACE, CALMS, VADER, complexity, LSP client
    dora/               # lead time, cycle time, rework rate, completion frequency
    space/              # performance, activity, communication, efficiency
    calms/              # automation, lean, measurement, sharing indicators
    sentiment/          # VADER integration, per-issue trajectory, anomaly detection
    difficulty/         # composite difficulty score
    complexity/         # churn, file size, indentation depth, change coupling
    lsp/                # LSP JSON-RPC client for language-specific metrics
    report/             # aggregates all domains into human and JSON output
  docs/                 # directory scaffolding, health checks, validation
  lineage/              # blame-to-issue mapping, coupling graph
  actor/                # worker identity parsing (type:identifier format)
```

Each plugin binary is a thin `main.go` that wires its internal package with Cobra commands. Plugins import the shared domain packages (`internal/issue`, `internal/milestone`, `internal/storage`) directly — the monorepo advantage.

Crochet, in its separate repo, consumes chain state through `git zhi` CLI JSON output. This is the porcelain/plumbing boundary.

## Phase 1: Data Model Enrichment

The largest phase. Extends the two core domain models and fixes session wiring.

### Issue Model Changes

**New frontmatter fields:**

| Field | Type | Default | Purpose |
|-------|------|---------|---------|
| `urgency` | enum (high, normal, low) | normal | Scope cutting guidance when fever chart goes red |
| `transitions` | []Transition | [] | Audit trail of state changes with actor identity |
| `observed_paths` | []string | [] | Actual files touched, recorded at `--state done` |

**Transition structure:**

```yaml
transitions:
  - state: start
    actor: "human:perigrin"
    timestamp: "2026-03-16T10:30:00Z"
  - state: done
    actor: "agent:claude-code-1"
    timestamp: "2026-03-16T14:22:00Z"
```

The `internal/actor/` package derives actor identity from git config (`user.name`/`user.email`) and formats the `type:identifier` convention. Type is `human` or `agent`; unrecognized patterns default to `human`.

**State machine addition:**

```
done ──→ reopened ──→ in-progress
```

- `done → reopened` via `--state reopen`
- `reopened → in-progress` via `--state start`

The `reopened` state records rework. Sanbao uses done→reopened transitions to compute rework rate (a DORA change failure rate proxy).

**New markdown sections:**

`## Steps` — checkbox list between Context and Acceptance Criteria, parsed by `ParseSections()`. Steps guide work but never gate state transitions (unlike ACs).

```markdown
## Steps
- [ ] Write test for positional param parsing
- [ ] Verify test fails
- [ ] Implement ParseSignature with positional support
- [ ] Verify test passes
- [ ] Commit
```

`### Positive Scenarios` / `### Negative Scenarios` — subsections under `## Acceptance Criteria`. Both use the same backtick-command convention. `--format json` exposes them as separate arrays. Flat AC lists (v0.1 format) are treated as positive scenarios for backward compatibility.

**Observed paths recording:**

`git zhi issue edit <id> --state done` records the files touched during the issue's sessions:

```
git diff --name-only <first_session_start_sha>..<last_session_end_sha>
```

Stored as `observed_paths` on the issue. Parallelization analysis uses the union of `context.paths` and `observed_paths` to assess overlap risk.

### Milestone Model Changes

**New fields:**

| Field | Type | Default | Purpose |
|-------|------|---------|---------|
| `state` | enum (open, completed) | open | Lifecycle tracking |
| `completed` | timestamp | null | Recorded when milestone completes |

**Format change:** Milestones switch from pure YAML to YAML frontmatter + markdown body, mirroring issues. The body carries milestone-level context:

```yaml
name: "v0.1"
state: open
due: "2026-04-15"
resolution: "make integration-test"
created: "2026-03-14T10:00:00Z"
completed: null
---

## Context

Single Go binary at cmd/git-zhi/main.go. Cobra root command with
subcommand groups.

## File Structure

  cmd/git-zhi/main.go
  internal/cli/root.go, issue.go, milestone.go

## Design Rationale

Issues ordered so storage is built first, then domain types,
then CLI wiring, then integration verification.
```

`resolution` changes from a freeform note to an executable command string. `milestone.Parse()` and `milestone.Marshal()` adopt the YAML-frontmatter+markdown pattern.

**Backward compatibility:** `milestone.Parse()` detects pure YAML (v0.1) or frontmatter+body (v0.2) and handles both. Missing fields default: `state` → open, `completed` → null.

### JSON Output Enhancement

`git zhi issue show --format json` embeds the parent milestone's body alongside the issue data. Workers receive three context layers without consulting external docs: repo-level (CONTRIBUTING.md), milestone-level (milestone body), issue-level (issue body).

### Session Wiring Fix

v0.1's pause/resume transitions validate state but never create or close session records. v0.2 fixes this:

- `--state start`: creates a new session with `start_sha` = current HEAD, `started_at` = now
- `--state pause`: closes the current session with `end_sha` = current HEAD, `ended_at` = now, `commits` = count
- `--state resume`: creates a new session (same as start)
- `--state done`: closes the current session (same as pause)

Telemetry, observed_paths, and lineage all depend on accurate sessions.

## Phase 2: Milestone Completion Gates

Enforces milestone lifecycle gates.

**`git zhi milestone edit <name> --resolve`:**
1. Reads the milestone's `resolution` field
2. Executes it as a shell command in the repo root
3. Reports pass/fail with stdout/stderr
4. Records result (leaves milestone state unchanged)

**`git zhi milestone edit <name> --state complete`** enforces three gates:

| Gate | Requirement | Failure behavior |
|------|-------------|------------------|
| Issues | All issues done or cancelled | Lists blocking issues |
| Resolution | Resolution command passed | Shows command output |
| Verify | `git zhi verify <name>` reports no regressions | Shows regression summary |

If verify is absent from `$PATH`, the gate is skipped with a warning.

A completed milestone rejects further issue additions. `git zhi issue edit <id> --milestone <completed>` returns an error.

## Phase 3: git-zhi-verify Plugin

Binary at `cmd/git-zhi-verify/`, domain logic in `internal/verify/`.

### AC Command Parser

Reads done issues in a milestone, extracts backtick-delimited commands from `## Acceptance Criteria`. Handles both v0.2 subsections (`### Positive Scenarios`, `### Negative Scenarios`) and v0.1 flat format (treated as positive).

AC parsing lives as a method on the issue's parsed sections, shared by verify, sanbao, and Crochet.

### Prioritized Execution Order

1. **Observed overlap:** issues whose `observed_paths` overlap with files changed since the issue was marked done (`git diff --name-only <done_sha>..HEAD`)
2. **Lineage coupling:** issues with lineage connections to recently completed issues (available after Phase 5; skipped until then)
3. **Remaining:** all other done issues in topological order

### Command Executor

- Runs each command via `os/exec` in the repo root
- Default timeout: 5 minutes, configurable via `git config zhi.verify.timeout`
- Captures stdout/stderr for reporting
- `--fail-fast`: stops on first failure
- `--dry-run`: lists commands without executing

### Output

Human format: per-issue, per-subsection pass/fail. Shows command output on failure.

JSON format: structured results array with issue ID, subsection, command, exit code, output.

Exit code: 0 = all pass, 1 = regressions detected.

## Phase 4: Parallelization

Exposes the DAG's implicit parallelism and adds multi-worker awareness.

### Ready Set with Path Analysis

`git zhi list --ready` returns the ready set enriched with path overlap data. The graph package gains:

```go
func (g *Graph) ParallelAssignment(
    ready []uuid.UUID,
    workerCount int,
    pathsFn func(uuid.UUID) []string,
) [][]uuid.UUID
```

Accepts the ready set, a worker count, and a function returning the union of `context.paths` + `observed_paths` per issue. Returns groups of non-overlapping issues safe for parallel execution.

Path overlap compares at both file and directory levels — `internal/parser/signature.go` overlaps with `internal/parser/errors.go` because they share `internal/parser/`.

### Multi-Worker WIP Semantics

v0.1: WIP = 1 globally, `Head()` returns the single in-progress issue.

v0.2: WIP = 1 per worker. `Head()` accepts an optional actor filter.

- With `--actor "agent:claude-code-1"`: returns that worker's in-progress issue, or picks from the ready set excluding issues in-progress by other workers.
- Without `--actor`: v0.1-compatible behavior (any in-progress issue is HEAD).

### Completion Forecasting

`git zhi milestone show <name> --workers N` adds forecast output:

- **Sequential time** = critical chain length x (1/speed)
- **Parallel speedup** bounded by ready set width and path overlap
- **Coordination tax** — initially a fixed heuristic (10% per parallel pair), refined from telemetry over time
- **Floor** = critical chain length regardless of worker count

### CLI Changes

| Command | Change |
|---------|--------|
| `git zhi list --ready` | New flag: shows ready set with path analysis |
| `git zhi next --actor <identity>` | Per-worker HEAD resolution |
| `git zhi milestone show --workers N` | Forecast with worker count |

## Phase 5: Lineage Tracking

New package `internal/lineage/`. A second DAG alongside the dependency graph — observed after work completes, driving context enrichment.

### Blame-to-Issue Mapping

Computed at read time on `git zhi issue show`:

1. Read the issue's `context.paths`
2. Run `git blame` scoped to those files
3. Map blame SHAs to issue sessions (index of `{SHA range → issue ID}` built from all done issues)
4. Return upstream issues with line counts per file

```go
type LineageEntry struct {
    UpstreamIssueID uuid.UUID
    Title           string
    FilePath        string
    LineCount       int
}
```

### Output

Human format: "Upstream lineage" section on `issue show` listing prior issues and line counts.

JSON format: includes titles, acceptance criteria, and context from upstream issues. Workers receive full upstream context automatically.

### Consumers

| Consumer | Use |
|----------|-----|
| git-zhi core | Context enrichment on `issue show` |
| verify | Prioritized execution (tier 2: lineage coupling) |
| sanbao | Coupling analysis, change coupling trends |

### Characteristics

- Dependency graph: declared, acyclic by invariant, drives scheduling
- Lineage graph: observed, typically acyclic but cycles are valid (high coupling signal), drives context

At v0.2 scale (tens to low hundreds of issues), blame scoped to `context.paths` runs fast enough without caching.

## Phase 6: Planning Telemetry

Extends `internal/telemetry/` with forecast and parallelization metrics.

### Forecast Accuracy

After milestone completion, record predicted vs actual:

```yaml
forecast_history:
  - predicted_weeks: 3.2
    actual_weeks: 4.1
    workers: 1
    recorded_at: "2026-04-15T10:00:00Z"
```

Stored on the milestone. Across milestones, forecast accuracy improves as telemetry accumulates.

### New Indicators

| Indicator | Computation | Recorded |
|-----------|-------------|----------|
| Forecast accuracy | predicted vs actual per milestone | At milestone completion |
| Ready set width | average and peak simultaneously executable issues | At milestone completion (summary) |
| Path overlap | count of parallel-eligible pairs with shared paths | At milestone completion (summary) |
| Parallel efficiency | actual vs theoretical completion time | At milestone completion |
| Lineage depth | upstream issue count per file in context.paths | Computed at read time |

Summary recording at milestone completion keeps the design simple. Crochet's postmortem adds qualitative context.

## Phase 7: git-zhi-sanbao Plugin

Binary at `cmd/git-zhi-sanbao/`, domain logic in `internal/sanbao/`. Read-only — never writes to `refs/zhi/`.

### Package Structure

```
internal/sanbao/
  dora/         # lead time, cycle time, rework rate, completion frequency
  space/        # performance, activity, communication, efficiency
  calms/        # automation, lean, measurement, sharing indicators
  sentiment/    # VADER integration, per-issue trajectory, anomaly detection
  difficulty/   # composite difficulty score
  complexity/   # churn, file size, indentation depth, change coupling
  lsp/          # LSP JSON-RPC client for language-specific metrics
  report/       # aggregates all domains into human and JSON output
```

### DORA Metrics

Derived entirely from issue state transitions — no new data collection.

| Metric | Derivation |
|--------|------------|
| Lead time | Issue `created` to `done` transition timestamp |
| Cycle time | `start` to `done` transition timestamp |
| Rework rate | done→reopened count / total done count |
| Completion frequency | Issues completed per calendar period |

### VADER Sentiment Analysis

Applies the Go VADER library to commit messages within issue session SHA ranges.

- **Per-issue trajectory:** sequence of compound scores across commits
- **Per-milestone summary:** aggregate sentiment across all issues
- **Anomaly detection:** compound < -0.1 for 3+ consecutive commits flags a warning

### Code Complexity

**Language-agnostic (always available):**
- File churn: modification count across session ranges
- File size: line count at milestone start vs completion
- Churn x size hotspots: product ranking
- Change coupling: co-occurrence matrix from commits
- Indentation depth: average and max nesting per file

**Language-specific (via LSP, when configured):**

Reads `zhi.lsp.<lang>` from git config, spawns the language server, sends `initialize`, and requests diagnostics and symbol information. Extracts cyclomatic complexity, diagnostic counts, and dead code.

LSP analysis is best-effort: missing server config falls back to churn-only analysis; server failure triggers a warning and continues.

Tests run against gopls on real test repo files.

### Issue Difficulty

Composite signal, normalized to 0–1:

| Factor | Weight direction |
|--------|-----------------|
| MPG (commits per issue) | Higher = harder |
| Cycle time | Longer = harder |
| Reopen count | Any reopen = harder |
| Mean sentiment | Lower = harder |
| Session count | More sessions = harder |

Informational only — never changes scheduling or gating. Feeds `crochet:postmortem` and `crochet:refinement`.

### CLI

```
git zhi sanbao report <milestone> [--format json]
git zhi sanbao report <milestone> --domain dora
git zhi sanbao report <milestone> --domain sentiment
```

## Phase 8: git-zhi-docs Plugin

Binary at `cmd/git-zhi-docs/`, domain logic in `internal/docs/`.

### Lazy Init

Any `git zhi docs` subcommand that finds no `docs/` directory scaffolds the canonical structure automatically, just as `git zhi issue add` bootstraps `refs/zhi/`. Living documents (`CONTRIBUTING.md`, `docs/contributing/coding-conventions.md`, `docs/contributing/development-workflow.md`) receive starter content — headings, placeholder sections, and `covers` frontmatter wired to common paths.

If `CONTRIBUTING.md` exists, lazy init adds the "Short Links to Important Resources" section linking to `docs/` subdirectories, preserving existing content.

### `git zhi docs init`

Explicit scaffolding command. Creates:

```
CONTRIBUTING.md
docs/
├── plans/
├── decisions/
├── contributing/
│   ├── coding-conventions.md
│   └── development-workflow.md
├── guides/
├── architecture/
└── reference/
```

Idempotent — creates only missing directories, proposes additions to existing files.

### `git zhi docs check`

Structural validation:

- Every file in `docs/` is reachable from CONTRIBUTING.md links
- ADR numbering in `docs/decisions/` is sequential with no gaps
- Every `covers` path in frontmatter resolves to an existing file or directory
- No dead links between documents
- Exit code: 0 = clean, 1 = issues found

### `git zhi docs health`

Churn-relative staleness detection:

- For each doc with a `covers` field, compute code churn since the doc's last modification via `git log --since=<date> --name-only -- <paths>`
- Drift levels: NONE (code unchanged), LOW (minor churn), HIGH (significant churn)
- Stability metadata modulates sensitivity — experimental docs flag sooner than stable docs
- ADRs and postmortems are exempt from staleness checks (append-only records)
- Coverage gap detection: packages with no architecture doc, new commands with no guide, milestones with no ADRs

### JSON Output

All three commands support `--format json`. Sanbao consumes this output as an engineering metric; `crochet:postmortem` uses it to identify drifted docs; `crochet:refinement` uses it to flag docs affected by planned work.

## Phase 9: Crochet (Separate Repo)

Claude Code plugin at `github.com/perigrin/crochet`. Skills and prompts, not Go code.

### crochet:refinement

Replaces `superpowers:writing-plans`. Transforms a brainstorming spec into an executable chain through four agent roles:

| Role | Responsibility | Chain interaction |
|------|---------------|-------------------|
| Architect | Reads spec + codebase, produces milestone context | `git zhi milestone add` |
| Decomposer | Breaks spec into issues with deps, context, Steps, positive ACs | `git zhi issue add` (batch via stdin) |
| SQE | Generates negative scenarios from spec + positive ACs (never sees code) | `git zhi issue edit` |
| Technical writer | Assesses doc impact, adds doc steps to code issues, creates standalone doc issues | `git zhi issue add`, `git zhi docs health --format json` |

**Lazy init:** On first run, inspects project structure, bootstraps CONTRIBUTING.md and CLAUDE.md if absent, and calls `git zhi docs init` for scaffolding.

All interaction flows through `git zhi` CLI commands. Crochet never accesses `refs/zhi/` directly.

### crochet:postmortem

Required at milestone completion. Structures the retrospective around four questions:

1. **What worked well?** — Clean execution, accurate decomposition, successful parallelization
2. **What didn't work?** — Worker struggles, decomposition errors, forecast misses
3. **What puzzles us?** — Unexpected patterns, anomalous telemetry, lineage surprises
4. **What will we do differently?** — Concrete process recommendations for future milestones

**Inputs (all via CLI):**
- `git zhi issue list --milestone <name> --format json`
- `git zhi milestone show <name> --format json`
- `git zhi verify <name> --format json`
- `git zhi docs health --format json`
- `git zhi sanbao report <name> --format json` (if available)
- `git log` on session SHA ranges

Produces markdown and attaches it via `git zhi milestone edit <name> --postmortem` (piped via stdin).

Subsequent `crochet:refinement` runs read past postmortems to avoid repeating process mistakes.

### Skill Structure

```
crochet/
  skills/
    refinement/     # skill definition + agent role prompts
    postmortem/     # skill definition + retrospective template
  README.md
```

## Cross-Cutting Concerns

### Backward Compatibility

v0.2 tools read v0.1 data and apply defaults for missing fields:

| Field | Default |
|-------|---------|
| `urgency` | normal |
| `transitions` | [] |
| `observed_paths` | [] |
| Milestone `state` | open |
| Milestone `completed` | null |
| Flat AC list (no subsections) | Treated as positive scenarios |
| Pure YAML milestone (no body) | Empty body |

v0.1 tools read v0.2 data by ignoring unknown fields. Schema version stays at 1.

### Testing

Same as v0.1: real on-disk git repos via `t.TempDir()`, no mocks. Each new package has its own test file.

Plugin integration tests build the binary and run it against test repos. Sanbao LSP tests run against gopls on real Go files. VADER tests use known commit messages with expected sentiment scores.

### Error Handling

Every plugin fails with clear diagnostics when chain state is unreadable. Read-only plugins (sanbao, docs) never mutate state — they report or error.

### Gate Degradation

| Gate | Missing plugin | Behavior |
|------|---------------|----------|
| Milestone completion → verify | verify not on `$PATH` | Gate skipped with warning |
| Postmortem → sanbao metrics | sanbao not on `$PATH` | Sanbao section omitted with warning |

Incremental adoption: core alone, core + verify, or full stack.

## Implementation Order

Nine phases in dependency order. Each phase is a milestone in git-zhi itself.

| Phase | Title | Depends on | Deliverable |
|-------|-------|------------|-------------|
| 1 | Data Model Enrichment | — | Issue + milestone model extensions, session wiring, actor package |
| 2 | Milestone Completion Gates | 1 | Resolution execution, gate enforcement |
| 3 | git-zhi-verify | 1, 2 | AC parser, command executor, prioritized ordering |
| 4 | Parallelization | 1 | Ready set exposure, path overlap, multi-worker WIP, forecasting |
| 5 | Lineage Tracking | 1 | Blame-to-issue mapping, context enrichment |
| 6 | Planning Telemetry | 1, 4, 5 | Forecast accuracy, parallel efficiency tracking |
| 7 | git-zhi-sanbao | 1, 5 | DORA, SPACE, CALMS, VADER, complexity, LSP, difficulty |
| 8 | git-zhi-docs | — | Scaffolding, validation, churn-relative health, lazy init |
| 9 | Crochet | 1–8 | refinement + postmortem skills (separate repo) |

Phase 8 (docs) has no dependency on earlier phases — it reads git history and filesystem, not `refs/zhi/` state transitions. It can start earlier for parallel development.

Phase 9 (Crochet) depends on all prior phases because it consumes JSON output from core, verify, sanbao, and docs.
