# v0.3 Implementation Design

v0.3 takes git-zhi from a small-team tool to one that works inside an existing enterprise ecosystem — Jira boards, GitLab forges, shared repos, cross-repo projects, stakeholder reporting. Nobody else changes their workflow. Scope is v0.3.0 (phases 1-9); v0.3.1 (calibration and validation) ships once real-world data exists.

## Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Scope | v0.3.0 only; v0.3.1 deferred | Calibration and validation require real-world data |
| Priority | Historian first | Bootstrap enabler — unlocks telemetry baselines for existing repos |
| Sequencing | Strict dependency order | Each phase completes its prerequisites before the next begins |
| Repo layout | Monorepo for all Go binaries | Same as v0.2 — shared internal packages, single test suite |
| Historian architecture | Core extension (not plugin) | Imports internal packages directly, shares write access with core |
| Jira testing | httptest.NewServer | Real HTTP stack with known responses, deterministic, no external deps |
| Jira import | Unix pipes: `git zhi jira LOPS-142 \| git zhi issue add` | Each tool does one thing; jira plugin emits YAML, core writes refs |
| Crochet v0.3 | Same pattern as v0.2 — skill definitions in separate repo | Skills and prompts at /home/perigrin/dev/crochet |
| Report templates | Crochet skill only, no Go binary | Template discovery is a convention, not a feature |
| Report storage | `docs/reports/` (repo) and `~/.config/zhi/reports/` (personal) | Convention-based; `git config` key for additional paths can come later |

## Phase Sequence (Dependency-Ordered)

```
Phase 1: Labels & Indexes (no deps)
    ↓
Phase 2: Multiplayer (needs labels for filtered capacity)
    ↓
Phase 3: Historian (needs labels for index building, multiplayer for assignment)
    ↓
Phase 4: Jira Sync (needs historian for import path)
    ↓
Phase 5: Project Aggregation (needs sync for cross-repo data, labels for filtering)
    ↓
Phase 6: Mermaid Visualization (needs project for cross-repo charts)
    ↓
Phase 7: Report Templates (Crochet skill, needs mermaid for charts)
    ↓
Phase 8: Crochet v0.3 Skills (needs historian for assess, sync for import)
    ↓
Phase 9: Onboard Skill Document (needs all prior phases)
```

Mermaid (Phase 6) is a pure formatter and can start earlier. Crochet skills (Phase 8) partially overlap with Phase 7.

## Privilege Boundary

| Component | Reads refs | Writes refs | Reads external APIs |
|-----------|-----------|-------------|-------------------|
| git-zhi core | yes | yes | no |
| git-zhi-historian | yes | yes (core extension) | no |
| git-zhi-verify | yes | no | no |
| git-zhi-sanbao | yes | no | no |
| git-zhi-docs | yes | no | no |
| git-zhi-jira | yes | no | yes (Jira REST) |
| git-zhi-project | yes (multi-repo) | no | no |
| git-zhi-mermaid | no (JSON stdin) | no | no |
| Crochet | via CLI JSON | via CLI commands | via MCP |

Only core and historian write to `refs/zhi/`. All other components read only.

## Phase 1: Labels & Indexes

**Data model:** Add `Labels []string` to Issue struct (`yaml:"labels,omitempty"`). Defaults to empty for backward compatibility.

**Index structure:** `refs/zhi/<label>/` contains lightweight refs pointing at issue refs. Indexes derive from `issue.Labels`, which is authoritative. Deleting and rebuilding an index yields identical results.

**CLI changes:**
- `--label <name>` filter on: `list`, `issue list`, `milestone show`, `next`
- `issue edit <id> --label <name>` and `--unlabel <name>`
- Filtered views show only matching issues; cross-label dependencies appear as external blockers with current state
- `git zhi config reindex` — scans all issues, rebuilds label indexes

## Phase 2: Multiplayer Enhancements

**Data model:** Add `Assigned string` to Issue struct (`yaml:"assigned,omitempty"`). Advisory only — any worker can start any ready issue.

**CLI changes:**
- `issue edit <id> --assign <worker>` and `--unassign`
- `issue list --assigned <worker>` filter
- `next --actor <identity>` prefers assigned issues when computing HEAD

**Capacity computation:** `milestone show` derives capacity at read time — per-worker in-progress count, assigned count, idle status. This phase covers single-repo contention only; cross-repo contention moves to Phase 5.

## Phase 3: git-zhi-historian (Core Extension)

The largest phase. Binary at `cmd/git-zhi-historian/`, domain logic in `internal/historian/`. Imports internal packages directly and enforces all graph invariants through the same code paths as core.

### Pipeline (Three Stages)

**Extract:** Parse `git log --use-mailmap` into structured commit data via go-git's commit walker. For each commit: author, timestamp, message, ticket references (regex for `[FOO-123]`, `FOO-123:`, `#123`), and diff fingerprint via `git show --numstat --name-status`.

**Cluster:** Greedy sequential with centroid coherence. Commits arrive in chronological order. Score each commit against open cluster centroids using six weighted signals:

| Signal | Weight | Rationale |
|--------|--------|-----------|
| `ticket_match` | 0.40 | Strongest when present — same ticket ID is near-definitive |
| `path_overlap` | 0.20 | Same files = probably same work |
| `diff_fingerprint` | 0.15 | Change shape catches cherry-picks and similar patterns |
| `time_proximity` | 0.10 | Close in time = likely related |
| `author_match` | 0.10 | Same author = weak signal |
| `message_tokens` | 0.05 | Shared words = weakest, breaks ties only |

Thresholds (provisional, calibrated in v0.3.1):
- Join threshold: 0.35
- Centroid coherence threshold: 0.25
- Inactivity gap: 14 days

All configurable via `refs/zhi/_/historian/config`.

**Enrich:** Convert clusters into retrospective issues. For each cluster: construct sessions from commit range boundaries, compute observed_paths as the union of all files touched, map actor via `actor.DeriveActor()`, set state to `done` with transitions reconstructed from timestamps, assign confidence and labels. Write issues through `internal/issue` and `internal/storage`.

### New Issue Fields (on Issue struct)

| Field | Type | Tag | Purpose |
|-------|------|-----|---------|
| `confidence` | float64 | `yaml:"confidence,omitempty"` | Historian's mapping reliability (0.0-1.0) |
| `source` | string | `yaml:"source,omitempty"` | Construction method: tracker-match, ticket-ref, cluster, single-commit, manual, planned |
| `tracker_id` | string | `yaml:"tracker_id,omitempty"` | External reference (e.g., `jira:LOPS-142`) |

The historian knows about git. It does not know about Jira, GitLab, or any external tracker. Tracker enrichment is a separate post-processing step handled by the sync plugin (Phase 4): `git zhi jira enrich <milestone>` reads historian-created issues and augments them with Jira metadata.

### CLI Commands

```
git zhi historian                                      # each commit as separate issue
git zhi historian --title-match "LOPS-*" --label LOPS  # match ticket refs from commit messages
git zhi historian --since 2025-01-01                   # time-bound
git zhi historian --dry-run                            # preview without writing
git zhi historian --incremental                        # only new commits since last run
git zhi historian triage                               # interactive mode (first interactive CLI in git-zhi)
git zhi historian status                               # coverage report
git zhi historian reindex                              # rebuild label indexes
```

### Interactive Triage (Pattern Introduction)

The triage subcommand introduces interactive terminal input to git-zhi for the first time. Prior commands are non-interactive (flags + stdin pipes). Triage presents commit clusters one at a time and reads single-character responses (`[a]ssign`, `[n]ew issue`, `[s]kip`, `[m]erge`, `[q]uit`) via `bufio.Scanner` on `os.Stdin`. This pattern may extend to other commands (e.g., interactive conflict resolution) but triage is the first instance.

### Progress Tracking

`refs/zhi/_/historian/last_processed_sha` tracks incremental progress. Before each incremental run, `git merge-base --is-ancestor` checks for history rewrites; if detected, the historian falls back to a full reprocess.

## Phase 4: Jira Sync (Reference Implementation)

Binary at `cmd/git-zhi-jira/`, domain logic in `internal/jira/`. Read-only on refs — translates between Jira's data model and zhi's YAML. The jira plugin never writes to `refs/zhi/`; all ref writes flow through core via Unix pipes.

### Sync Model

**Outbound (zhi → Jira):** Reads zhi state, pushes state changes to Jira via REST API. Git config maps states (`zhi.sync.jira.state.done = "Done"`). No ref writes — only HTTP writes to Jira.

**Inbound (Jira → zhi):** Reads Jira state, emits issue edit operations to stdout. Core writes the updates (including `last_synced_at` timestamps) via piped bulk edit:

```
git zhi jira sync pull | git zhi issue edit --batch    # Jira plugin emits, core writes refs
```

This preserves the privilege boundary: the jira plugin reads from both sides and emits operations; core handles all ref mutations. The `--batch` flag on `issue edit` accepts a stream of edit operations from stdin (a small core enhancement in this phase).

**Conflict resolution:** After each sync, the jira plugin stores a snapshot of synced field values per issue in `.git/zhi-sync/jira/<issue-id>.yaml` (local to the repo, not tracked in refs or committed). On the next sync, the plugin compares each field's current value in zhi and Jira against the snapshot to determine what changed on each side. If the same field changed on both sides, the sync flags a conflict. If different fields changed, both updates apply without conflict. The user resolves conflicts via `git zhi jira resolve <ticket> --keep-zhi | --keep-tracker`, which emits the resolution as an edit operation piped to core.

### Import via Unix Pipes

```
git zhi jira LOPS-142                        # fetch ticket, emit issue YAML to stdout
git zhi jira LOPS-142 | git zhi issue add    # pipe into issue creation
git zhi jira LOPS-142 --dry-run              # preview emitted YAML
```

The jira plugin emits; core writes. Same pattern for any future sync plugin (`git zhi gitlab`, `git zhi linear`).

### Identity Mapping

Git config maps git authors to Jira users:
```
git config zhi.sync.jira.actor.perigrin "chris.prather@example.com"
```

### Credentials

`ZHI_JIRA_TOKEN` env var takes precedence over `git config zhi.sync.jira.token`. Credentials never live in refs.

### CLI Commands

```
git zhi jira sync pull | git zhi issue edit --batch    # inbound: Jira → zhi (core writes)
git zhi jira sync push                                  # outbound: zhi → Jira (HTTP writes)
git zhi jira sync --dry-run                             # preview changes
git zhi jira resolve <ticket> --keep-zhi                # resolve conflict
git zhi jira resolve <ticket> --keep-tracker
git zhi jira LOPS-142                                   # emit issue YAML to stdout
git zhi jira enrich <milestone>                         # augment historian issues with Jira metadata
```

### Core Enhancement: `issue edit --batch`

Phase 4 adds a `--batch` flag to `git zhi issue edit` that reads a stream of edit operations from stdin. Each operation specifies an issue ID and the fields to update. This enables sync plugins to emit bulk updates without writing refs directly.

### Testing

All tests use `httptest.NewServer` with known Jira REST responses. Coverage: inbound pull (piped to batch edit), outbound push, conflict detection, identity mapping, credential handling, pagination.

## Phase 5: Project Aggregation

Binary at `cmd/git-zhi-project/`, domain logic in `internal/project/`. Reads chain state from multiple repos and computes cross-repo critical chain and CCPM buffers.

### Project Definition File (YAML)

```yaml
name: Auth Overhaul
repos:
  - path: ~/dev/service-auth
    milestone: v2.1
  - path: ~/dev/service-api
    milestone: v3.0
    feeds:
      - repo: service-auth
        buffer: 3d
workers:
  - name: dev-a
    repos: [service-auth, service-api]
```

### CCPM Buffers (Goldratt Standard)

- **Project buffer:** 50% of cross-repo critical chain duration. GREEN < 1/3, YELLOW 1/3-2/3, RED > 2/3.
- **Feeding buffers:** 50% of feeding chain duration at each cross-repo junction. Same thresholds.
- **Resource buffers:** Binary signal (on track / at risk) at shared-worker handoff points.

### CLI Commands

```
git zhi project show <file>                     # full project status
git zhi project show <file> --format json       # structured output
git zhi project next --actor <name> <file>      # cross-repo "what's next"
```

### How It Reads Chain State

Opens each repo's `.git`, creates a `storage.Store`, and reads through internal packages. Monorepo-safe — imports `internal/storage`, `internal/issue`, etc.

## Phase 6: Mermaid Visualization

Binary at `cmd/git-zhi-mermaid/`, domain logic in `internal/mermaid/`. Pure formatter — JSON in, Mermaid text out. Touches neither git nor refs.

### Two Chart Types

**Gantt with resource lanes:**
```
git zhi list --format json | git zhi mermaid gantt
```

Lanes derive from the `assigned` field or last transition actor.

**DAG visualization:**
```
git zhi list --format json | git zhi mermaid dag
```

Status icons: ✓ done, 🔵 in-progress, ◻️ pending, ✗ cancelled.

### CLI

```
git zhi mermaid gantt                   # reads stdin JSON
git zhi mermaid gantt --file data.json  # reads file
git zhi mermaid dag                     # DAG from stdin
```

Mermaid emits text — the destination (GitHub, Confluence, browser) handles rendering.

## Phase 7: Report Templates (Crochet Skill Only)

No Go binary. The `crochet:report` skill reads user-defined templates (YAML frontmatter + prompt + structure), executes declared CLI commands to collect data, and synthesizes narrative reports with embedded Mermaid charts.

**Template discovery:** `docs/reports/` (per-repo) and `~/.config/zhi/reports/` (personal). Convention-based, with no Go enforcement.

**Template format:**

```yaml
---
name: recurring-status
data:
  - git zhi project report auth-overhaul --format json
  - git zhi sanbao report HEAD --format json
schedule: recurring
---

## Prompt

Professional tone, lead with what shipped...

## Structure

### Summary
### What Shipped
### Risks & Blockers
### Forecast
```

Structure is authoritative — the LLM produces exactly these sections in this order. The prompt guides narrative tone within that structure.

## Phase 8: Crochet v0.3 Skills

Three new skills in the crochet repo:

**`crochet:assess`** — Reads a PRD and analyzes the codebase for gaps. Four categories: Missing, Partial, Blocking, Ready. Draws lineage data from `git zhi issue list --format json`. Output feeds `crochet:refinement`.

**`crochet:import`** — Assisted ticket import. Runs `git zhi jira <ticket>`, reads existing chain state, and proposes dependencies and urgency from path overlap. Presents the enriched issue for review, then pipes to `git zhi issue add` on approval.

**`crochet:onboard`** — Executes the onboard procedure. Runs the full adoption walkthrough, requiring human approval at each decision point.

**Skill structure (additions to crochet repo):**
```
crochet/
  skills/
    refinement/     # existing (v0.2)
    postmortem/     # existing (v0.2)
    report/         # new — template-based narrative reports
    assess/         # new — PRD vs codebase gap analysis
    import/         # new — assisted ticket import
    onboard/        # new — automated adoption walkthrough
```

## Phase 9: Onboard Skill Document

Documentation, not code. A human-executable procedure that `crochet:onboard` can automate.

Lives at `skills/onboard/procedure.md` in the crochet repo. Steps:

1. Assess current state (existing docs, refs, tracker)
2. Scaffold documentation (`git zhi docs init`)
3. Bootstrap history (`git zhi historian --title-match ... --dry-run`, then for real)
4. Check coverage (`git zhi historian status`, triage if needed)
5. Configure sync (optional: `git config zhi.sync.jira.*`, dry-run)
6. Verify baseline (`git zhi sanbao report`)
7. Start working (`git zhi next`)

Each step has: what to run, what to expect, how to verify, how to rollback.

All new fields default gracefully:

| Field | Default |
|-------|---------|
| `labels` | [] |
| `assigned` | "" |
| `confidence` | 0 |
| `source` | "planned" for new issues, "" for v0.1/v0.2 issues |
| `tracker_id` | "" |
| `last_synced_at` | nil |

Schema version remains 1. v0.2 tools ignore unknown fields.
