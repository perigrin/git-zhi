## Postmortem: Four Questions

### What worked?

1. **Pipeline ran end-to-end on the execute PRD.** Pushback → refinement →
   alignment → execution. Each step caught something the previous missed:
   pushback found CLI flag errors and missing safety valves, alignment found
   stale AC text and missing tier-2/idempotency coverage.

2. **Pushback found real API mismatches.** Three of five pushback findings
   were valid (two-step reopen, sanbao scope, max reopens). The fourth
   (`chain list --ready`) was wrong — the Explore agent misread the codebase.
   Caught during refinement when `git zhi chain list` didn't exist.

3. **Sanbao gate analyst design converged through iterative brainstorming.**
   Started with hardcoded heuristics ("> 3 files"), evolved to sanbao-driven
   measured complexity. The brainstorm → pushback → refinement cycle worked
   as intended.

4. **PAAD gate validation was clean.** The two-step reopen flow
   (done → reopen → start) works correctly. Body append via `--body` on stdin
   works. The `### Review Findings` section survives round-trip through
   issue persistence.

### What didn't work?

1. **Pushback's Explore agent gave a false finding.** It claimed `--ready`
   lives on `git zhi chain list`, not `git zhi list`. This was wrong —
   `--ready` is on `list`. The overcorrection propagated to both PRD and
   skill files before being caught during refinement. Subagent findings need
   verification against the actual binary, not just code search.

2. **Batch-add still defaults to sequential.** The v0.3.4 issues were created
   before rebuilding the binary with v0.3.3 changes. Same chicken-and-egg
   problem as v0.3.3 — always rebuild and install before creating issues.

3. **Dependency wiring with --block vs --after was confusing.** Three attempts
   to wire the DAG correctly. `--block X` means "this blocks X" (forward),
   `--after X` means "X blocks this" (backward). The semantic mismatch caused
   inverted graphs. The flag names are not intuitive.

4. **v0.3.4 was design-heavy, validation-light.** Most work was in the
   brainstorming and design sessions. The issues themselves were trivial to
   close. This is appropriate for a design milestone but means the sanbao
   telemetry is less meaningful (MPG 0.0, difficulty 0.09).

### What puzzles us?

1. **Sanbao hotspot scoping.** The gate analyst simulation on v0.3.3 showed
   ALL issues as tier-2 because hotspots are computed at milestone scope, not
   per-issue. If every issue in a hotspot-heavy milestone triggers tier-2,
   the tiering is useless. Need per-issue hotspot scoping or a different
   metric for the gate analyst.

2. **Ralph Loop validation was structural, not behavioral.** We verified the
   setup script accepts `--completion-promise` and `--max-iterations`, but
   couldn't launch a Ralph Loop within the session to test actual termination.
   The v0.3.3 session exercised Ralph Loop successfully, but the v0.3.4
   validation issue is weaker than ideal.

### What should we change?

1. **Always rebuild before creating issues.** This is the third time we've
   hit the stale-binary problem. Add it to the crochet:refinement skill as
   a prerequisite step.

2. **Verify subagent findings against the running binary.** When the Explore
   agent reports CLI flags, run the actual `--help` command to confirm before
   modifying the PRD.

3. **Add per-issue hotspot scoping to sanbao.** Either a `--issue` filter or
   a per-issue hotspot breakdown in the report. Without this, the gate
   analyst tiering is milestone-dependent rather than issue-dependent.

4. **Consider a "design milestone" template** that skips sanbao-heavy
   validation AC (since design milestones produce no code commits) and
   focuses on artifact quality (skill text, PRD correctness, API alignment).
