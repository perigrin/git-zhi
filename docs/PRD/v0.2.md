# git-zhi v0.2 — Scaling: Product Requirements Document

## Overview

v0.2 scales git-zhi from a solo developer’s task scheduler to a system that supports a small team — one or two developers working alongside one or two coding agents. It introduces quality gates that enforce rigor as work gets distributed, parallelization awareness so you know when a second worker (human or agent) actually helps, and tooling to go from a PRD to an executable chain without hand-crafting plan files.

Three coordinated components: enhancements to the git-zhi core binary for milestone gating, regression verification, parallelization analysis, and enriched issue/milestone formats; a separate observatory binary (sanbao — 三宝, “three treasures”) for engineering metrics; and Crochet, a Claude Code plugin that provides the intelligence layer — decomposing PRDs into executable chains and generating mandatory postmortems at milestone completion.

v0.1 answers “what should I work on next?” v0.2 answers “can a team execute this milestone end-to-end with quality gates, and how do we know it went well?”

## Problem Statement

v0.1 works well for a solo developer walking the chain. But the moment you add a collaborator — whether that’s a coding agent running in a worktree, a second developer, or both — new problems emerge:

- **No plan decomposition.** Turning a spec into a chain of issues currently requires manual effort or static plan files that go stale the moment one task changes an interface. This is tolerable when you’re the only one working; it’s a bottleneck when you need to hand off work.
- **No integration gate.** Individual issues have acceptance criteria, but nothing verifies that completed issues still work together as a whole. When one person does everything sequentially, integration is implicit. With parallel workers, it’s not.
- **No regression detection.** After five issues merge, does issue three’s acceptance criteria still pass? A solo developer notices because they’re in the code. A second worker doesn’t have that context.
- **No parallelization awareness.** The DAG contains the information needed to determine which issues can be safely worked on simultaneously, but v0.1 doesn’t surface it. Without this, assigning parallel work risks merge conflicts and wasted effort.
- **No milestone lifecycle.** Milestones are passive groupings. There’s no ceremony around completion, no postmortem, no learning feedback loop. At solo scale, you carry the lessons in your head. At team scale, you need to capture them.
- **No quality metrics.** Speed and MPG tell you about throughput but nothing about code health, rework, or engineering effectiveness. When someone else is writing code in your project — especially an agent — you need visibility into quality, not just velocity.
- **Test theater.** When the same worker writes code and tests, the tests often validate tautologies. This is true of humans and doubly true of agents. Adversarial test scenarios need to come from a separate concern, generated before implementation begins.

## Design Principles

1. **One core binary, Go plugins, one Claude Code plugin, one data store.** git-zhi is the core scheduler that reads/writes `refs/zhi/`. git-zhi-verify, git-zhi-sanbao, and git-zhi-docs are optional Go plugins — standalone binaries following the `git-zhi-*` naming convention, discoverable via `$PATH`, invocable as `git zhi <name>`. Crochet is a Claude Code plugin that accesses chain state exclusively through `git zhi` CLI commands — the same porcelain-over-plumbing pattern git itself uses. Clean separation of concerns, independent release cadences.
1. **Deterministic plumbing, intelligent porcelain.** git-zhi and its Go plugins (verify, sanbao, docs) are pure Go — no LLM dependencies, work offline. Crochet is the LLM-powered layer, running as a Claude Code plugin.
1. **Human and agent parity.** Every feature serves both humans and agents. A developer checking `git zhi list --ready` gets the same parallelization guidance as an orchestrator script. Metrics capture signals from both human and agent work. The workflow doesn’t care who’s doing the work.
1. **Algorithmic quality enforcement.** Quality gates are architectural, not advisory. Milestone completion is gated on resolution commands and verification passes. The system enforces rigor rather than hoping for it.
1. **The system learns.** Postmortems feed back into CONTRIBUTING.md. Past milestone data informs future decomposition. Forecast accuracy improves over time.

## Technical Conventions

### Plugin Discovery

Go plugins follow git’s subcommand discovery convention: any executable named `git-zhi-<name>` on `$PATH` is invocable as `git zhi <name>`. This is the same pattern used by `git-lfs`, `git-filter-repo`, and git’s own subcommand discovery. No registration or configuration required — presence on `$PATH` is sufficient.

```
git-zhi-verify   → git zhi verify
git-zhi-sanbao   → git zhi sanbao
git-zhi-docs     → git zhi docs
```

### Configuration Namespace

All zhi configuration uses the `zhi.*` namespace in git config:

```bash
git config zhi.verify.timeout 300        # verify command timeout in seconds
git config zhi.lsp.go "gopls"            # LSP server for Go files
git config zhi.lsp.perl "PLS"            # LSP server for Perl files
git config zhi.lsp.typescript "typescript-language-server"
```

Configuration follows git’s standard precedence: repository-level (`.git/config`), user-level (`~/.gitconfig`), system-level (`/etc/gitconfig`).

### Schema Versioning

The chain config ref (`refs/zhi/_/config`) includes a schema version field. v0.1 is version 1. v0.2 additions are backward-compatible — v0.2 tools can read v0.1 data, and v0.1 tools can read v0.2 data (ignoring fields they don’t recognize). If a future version requires a breaking schema change, the version field enables migration tooling.

### Session Bookmark Semantics

Sessions are the measurement windows that drive telemetry. Session boundaries are deterministic:

- **Session starts** when `git zhi issue edit <id> --state start` is executed. The current HEAD SHA is recorded as `start_sha`. Timestamp is recorded as `started_at`.
- **Session pauses** when `--state pause` is executed. HEAD SHA recorded as `end_sha`, timestamp as `ended_at`. State remains in-progress.
- **Session resumes** when `--state resume` is executed. A new session entry is created with the current HEAD SHA.
- **Session ends** when `--state done` is executed. Final HEAD SHA and timestamp recorded.

Commits between `start_sha` and `end_sha` in each session feed MPG, sentiment analysis, and lineage computation. Commits outside any session’s range are shadow work.

## Scheduler Algorithm

The scheduler determines what to work on next. It is deterministic — given the same chain state, it always produces the same answer.

**WIP semantics:** In v0.1, WIP limit = 1 for the entire chain (solo developer). In v0.2, WIP limit = 1 *per worker*. The chain can have multiple in-progress issues simultaneously (one per worker), but no single worker has more than one in-progress issue. This is a semantic change: HEAD in v0.1 resolved to *the* in-progress issue. In v0.2, HEAD resolves based on the caller’s identity — your in-progress issue, or the next ready issue if you don’t have one.

```
function next_issue(chain, caller_actor):
    all_issues = read_all_issues(chain)

    # 1. If this worker already has an in-progress issue, that's their HEAD
    my_issue = [i for i in all_issues
                where i.state == in-progress
                and i.transitions.last.actor == caller_actor]
    if my_issue:
        return my_issue[0]  # WIP limit = 1 per worker

    # 2. Build the ready set (exclude issues in-progress by other workers)
    in_progress_ids = {i.id for i in all_issues where i.state == in-progress}
    ready = [i for i in all_issues
             where i.state == pending
             and i.id not in in_progress_ids
             and all(dep.state in {done, cancelled}
                     for dep in i.blocked_by)]

    # 3. If nothing is ready, chain is blocked or complete
    if not ready:
        return nil

    # 4. Find which ready issues are on the critical chain
    critical = critical_chain(all_issues)
    critical_ready = [i for i in ready where i in critical]

    # 5. Among critical-ready issues, pick the one with the most
    #    downstream dependencies (maximizes unblocking)
    if critical_ready:
        return max(critical_ready, key=downstream_count)

    # 6. No critical-ready issues — pick any ready issue
    #    (off-chain work, safe to parallelize)
    return ready[0]  # by UUIDv7 order (creation time)
```

When called without actor identity (solo developer, backward-compatible), the function behaves as v0.1: any in-progress issue is HEAD, WIP = 1 for the chain.

**Path-overlap filtering for parallel assignment (v0.2):**

```
function parallel_assignment(ready, worker_count):
    assigned = []
    used_paths = {}

    for issue in ready (sorted by critical_chain_position):
        issue_paths = union(issue.context.paths, 
                           historical_observed_paths(issue.context.paths))
        if no overlap between issue_paths and used_paths:
            assigned.append(issue)
            used_paths.update(issue_paths)
        if len(assigned) >= worker_count:
            break

    return assigned
```

Issues with overlapping paths (declared or historically observed) are never assigned to concurrent workers. The first issue in critical chain order gets priority; subsequent issues are assigned only if their paths don’t conflict.

## Components

### 1. git-zhi (Go binary) — Scheduler

The core binary gains milestone lifecycle management, enriched data formats, parallelization analysis, lineage tracking (an observed coupling graph derived from `git blame` that enriches issue context with upstream history), and planning-relevant telemetry.

### 2. git-zhi-verify (Go plugin) — Regression Verification

A `git-zhi-*` plugin (invocable as `git zhi verify`) that parses backtick-delimited commands from acceptance criteria on done issues, executes them, and reports pass/fail. Deterministic — no LLM needed.

### 3. git-zhi-sanbao (Go plugin) — Observatory

A `git-zhi-*` plugin (invocable as `git zhi sanbao`) that reads `refs/zhi/` and computes engineering health metrics: DORA, SPACE, CALMS indicators, code complexity signals (language-agnostic via churn analysis, language-specific via LSP), and commit-level analysis.

### 4. git-zhi-docs (Go plugin) — Documentation Health

A `git-zhi-*` plugin (invocable as `git zhi docs`) that scaffolds and validates a canonical `docs/` directory structure, monitors documentation health relative to code churn, and tracks stability metadata. Deterministic — no LLM needed.

### 5. Crochet (Claude Code plugin) — Intelligence

A Claude Code plugin providing skills and prompts that bridge specs and executable chains. Crochet is not a binary — it’s an LLM-powered layer that interrogates and modifies chain state through `git zhi` CLI commands (`git zhi issue add`, `git zhi milestone add`, `git zhi list --format json`, etc.). Includes four agent roles in its decomposition skill: architect, decomposer, SQE, and technical writer. Replaces `superpowers:writing-plans` in the Obra Superpowers workflow.

## git-zhi Core Enhancements

### Milestone Lifecycle

Milestones gain an explicit lifecycle and completion gates.

```
open → completed
```

`git zhi milestone edit v0.1 --state complete` enforces:

1. All issues in the milestone are done or cancelled
1. The resolution command has been executed and passed
1. `git zhi verify v0.1` reports no regressions

If any gate fails, completion is refused with a diagnostic message explaining what’s blocking.

### Milestone Body

Milestones gain a markdown body alongside their YAML frontmatter, following the same pattern as issues. The body carries architectural context that applies to all issues in the milestone.

```yaml
name: "v0.1"
due: "2026-04-15"
resolution: "make integration-test"
created: "2026-03-14T10:00:00Z"
---

## Context

Single Go binary at cmd/git-zhi/main.go. Cobra root command with
subcommand groups. Internal packages under internal/ own domain logic.

## File Structure

  cmd/git-zhi/main.go
  internal/cli/root.go, issue.go, milestone.go, chain.go
  internal/storage/store.go
  internal/issue/issue.go
  internal/graph/graph.go

## Design Rationale

Issues are ordered so that storage is built first (no deps),
then domain types, then CLI wiring, then integration verification.
The critical chain runs through storage → issue → CLI.
```

When an agent picks up an issue via `git zhi issue show --format json`, the JSON output includes the parent milestone’s context. The agent receives three layers of context without consulting any external documents: repo-level from CONTRIBUTING.md (via CLAUDE.md), milestone-level from the milestone body, and issue-level from the issue itself.

### Issue Format Enhancements

#### Steps Section

Issues gain an optional `## Steps` section between Context and Acceptance Criteria. This is the mini-plan choreography — the sequence of actions needed to complete the issue, following a RED-GREEN-COMMIT cadence.

```markdown
## Steps
- [ ] Write test for positional param parsing
- [ ] Verify test fails (function doesn't exist yet)
- [ ] Implement ParseSignature with positional support
- [ ] Verify test passes
- [ ] Write test for error messages with line numbers
- [ ] Verify test fails
- [ ] Add line tracking to parser errors
- [ ] Verify test passes
- [ ] Run full test suite
- [ ] Commit
```

Steps are tracked as checkboxes. The executing agent checks them off as work progresses. Steps are informational — unlike acceptance criteria, unchecked steps do not gate state transitions. They guide the work but don’t enforce completion order.

#### Acceptance Criteria Subsections

Acceptance criteria split into positive and negative scenarios:

```markdown
## Acceptance Criteria

### Positive Scenarios
- [ ] positional params work (`go test -run TestSignature_Positional -v`)
- [ ] error messages include line numbers (`go test -run TestSignature_Errors -v`)
- [ ] handles named params with defaults (`go test -run TestSignature_Named -v`)

### Negative Scenarios
- [ ] rejects duplicate param names with clear error (`go test -run TestSignature_DuplicateParam -v`)
- [ ] handles EOF mid-signature without panic (`go test -run TestSignature_EOF -v`)
- [ ] returns meaningful error for unresolvable param types (`go test -run TestSignature_BadType -v`)
- [ ] survives empty signature () (`go test -run TestSignature_Empty -v`)
- [ ] rejects circular default references (`go test -run TestSignature_CircularDefault -v`)
```

Both subsections use the same backtick-command convention from v0.1. `git zhi verify` treats them identically — it runs every command and reports pass/fail. The `--format json` output exposes them as separate arrays so agents and metrics tools can distinguish pass rates by category.

The distinction exists for two reasons. First, the generating agent (the SQE role in `crochet:refinement`) produces negative scenarios from a different perspective than the decomposer agent that produces positive scenarios — separation of concerns prevents test theater. Second, the executing agent needs to know it must handle failure modes, not just the happy path.

#### Urgency Metadata

Issues gain an optional `urgency` field in frontmatter:

```yaml
---
title: "Parse basic signatures"
urgency: high    # high | normal | low
---
```

Urgency interacts with scope cutting. When the fever chart goes red, `git zhi milestone show` recommends cutting low-urgency issues that aren’t on the critical chain first. The recommendation algorithm considers both urgency and graph position — a low-urgency issue with many downstream dependencies is harder to cut than one with none.

#### Issue State Machine (v0.2 additions)

The v0.1 PRD defines the core state transitions:

```
pending ──→ in-progress ──→ done
                │   ▲
           start│   │resume
                │   │
           pause│   │
                ▼   │
            (still in-progress,
             measurement paused)

pending ──────────────────→ cancelled
in-progress ──────────────→ cancelled
cancelled ── ($EDITOR) ───→ pending
```

v0.2 adds one transition for rework tracking:

```
done ──→ reopened ──→ in-progress
```

A `reopened` state records that the issue was previously marked done but required additional work. This is distinct from `pending` — the issue has history. Sanbao uses done→reopened transitions to compute rework rate (a DORA change failure rate proxy). The reopened→in-progress transition follows automatically when the worker starts the rework.

Valid state transitions (complete v0.2 list):

|From                |To                  |Trigger           |
|--------------------|--------------------|------------------|
|pending             |in-progress         |`--state start`   |
|in-progress         |in-progress (paused)|`--state pause`   |
|in-progress (paused)|in-progress         |`--state resume`  |
|in-progress         |done                |`--state done`    |
|pending             |cancelled           |`--state cancel`  |
|in-progress         |cancelled           |`--state cancel`  |
|cancelled           |pending             |`$EDITOR` (manual)|
|done                |reopened            |`--state reopen`  |
|reopened            |in-progress         |`--state start`   |

Any transition not in this table is rejected.

#### Worker Identity

Issue state transitions record the actor who triggered them:

```yaml
transitions:
  - state: start
    actor: "agent:claude-code-1"
    timestamp: "2026-03-15T10:30:00Z"
  - state: done
    actor: "human:perigrin"
    timestamp: "2026-03-15T14:22:00Z"
```

Actor identity is derived from git author configuration (`user.name` / `user.email`). The `actor` field uses a `type:identifier` format where type is `human` or `agent`. Agents are expected to configure a distinguishable git identity (e.g., `Claude Code <claude-code@agent>`). If the type cannot be determined, it defaults to `human`.

Sanbao uses actor identity to compute agent autonomy rate (issues where all state transitions were triggered by agents), distinguish sentiment patterns between human and agent workers, and track per-worker throughput.

### Parallelization Analysis

The DAG already encodes which issues can run in parallel (no shared `blocked_by` edges). v0.2 adds `context.paths` overlap detection to identify merge-conflict risk between parallel-eligible issues.

#### Ready Set with Path Analysis

```
$ git zhi list --ready

Ready set: 3 issues (no blocking dependencies)

  019444a3  Parse signatures        paths: internal/parser/signature.go
  019444a6  Config persistence      paths: internal/config/
  019444a8  Tag resolution          paths: internal/resolve/

  No path overlap detected. All 3 safe for parallel execution.
```

When paths overlap:

```
Ready set: 3 issues

  019444a3  Parse signatures        paths: internal/parser/signature.go
  019444a6  Parser error recovery   paths: internal/parser/errors.go, internal/parser/signature.go
  019444a8  Tag resolution          paths: internal/resolve/

  ⚠ Path overlap: 019444a3 ↔ 019444a6 share internal/parser/signature.go
    Recommend: sequence a3 before a6, parallelize a8 with either

  Max useful workers: 2
```

#### Observed Paths (Self-Correction)

`context.paths` are declared by the issue author (or by Crochet during decomposition). In practice, paths drift — developers forget files, agents guess wrong, refactors expand scope. When an issue is marked done, zhi records the actual files touched:

```bash
git diff --name-only start_sha..end_sha
```

These are stored as `observed_paths` on the issue. Parallelization analysis uses the union of `context.paths` and `observed_paths` from prior issues when assessing overlap risk for future work. The first milestone runs on declared paths alone; subsequent milestones benefit from observed reality. The system self-corrects as it accumulates data.

`observed_paths` also feeds lineage computation (blame is scoped to observed files, not just declared ones) and verify prioritization (ACs are ordered by file overlap with recent changes).

#### Completion Forecasting with Worker Count

`git zhi milestone show` gains a `--workers N` parameter. A worker is anyone doing issues — you, a colleague, a coding agent in a worktree:

```
$ git zhi milestone show v0.1 --workers 3

Forecast:
  At 1 worker:  ~3.2 weeks (critical chain: 6 issues)
  At 2 workers: ~2.1 weeks (1 off-chain parallel track)
  At 3 workers: ~1.9 weeks (diminishing returns — ready set rarely exceeds 2)

  Critical chain length sets the floor at ~1.8 weeks regardless of worker count.
  Path overlap on 2 issue pairs adds ~0.3 weeks coordination tax at 3 workers.
```

The model is a heuristic estimate, not an optimal schedule (DAG scheduling with resource constraints is NP-hard). Forecasts are derived from historical telemetry and improve as the system observes more milestones:

- **Sequential time** = critical chain length × (1 / speed)
- **Parallel speedup** = bounded by ready set width and path overlap
- **Coordination tax** = estimated merge conflict probability per parallel pair, refined from observed telemetry over time
- **Effective completion** = max(sequential_time, (off_chain_work / min(N, ready_set_width))) + coordination_tax

The critical chain length is always the floor. No amount of parallelism beats the longest sequential dependency path. This is Goldratt’s insight applied directly: the constraint is the critical chain, not the number of workers. Adding a second developer or a coding agent helps only when there’s off-chain work they can do without stepping on the critical path. Early milestones will have less data and less accurate forecasts; accuracy improves as telemetry accumulates.

### Lineage Tracking (Observed Coupling Graph)

Every experienced developer runs `git log` and `git blame` before modifying unfamiliar code — tracing who changed what and why. Zhi automates the cross-referencing: instead of reading raw blame output and mentally mapping SHAs to past work, it maps directly to issues with their titles, context, and decisions.

This is a second DAG, distinct from the dependency graph. The **dependency graph** is declared before work starts and drives scheduling (“B can’t start until A is done”). The **lineage graph** is observed after work completes and drives context enrichment (“B actually modified code that A introduced”).

#### How It Works

Each issue already records session bookmarks with start/end SHAs. When an issue is marked done, zhi can `git diff` to identify files and lines changed during that issue’s sessions, then `git blame` at the start SHA to trace which prior issues originally wrote the lines that were modified. The result is a directed graph of observed coupling: “issue D modified lines originally written by issues A, B, and C.”

This computation happens at read time, not write time. When a worker runs `git zhi issue show E`, zhi knows E’s `context.paths`, runs blame on those files, maps blame ranges back to issue sessions, and surfaces the relevant prior issues:

```
$ git zhi issue show E

  Parse signature error recovery
  ...

  ## Context

  - paths: internal/parser/signature.go, internal/parser/errors.go
  - commands: go test ./internal/parser/...
  - entrypoints: internal/parser/signature.go

  Upstream lineage (code you'll be modifying):
    019444a1  Implement lexer              → 12 lines in errors.go
    019444a3  Parse signatures             → 34 lines in signature.go
    019444a4  Error recovery foundations   → 18 lines in errors.go

  ...
```

In JSON output, lineage includes titles, acceptance criteria, and key context from upstream issues. A worker — human or agent — can see that issue A3 made a specific parser design choice and A4 established the error recovery pattern, and work *with* those decisions instead of accidentally undermining them.

#### Why It Matters at Small Team Scale

When you’re solo, you carry the lineage in your head. You wrote the code; you know why it’s shaped that way. The moment someone else touches it — a coding agent, a colleague, or even you six months later — that context is lost. Today developers recover it manually through `git blame` and archaeology. Zhi maps the blame output back to structured issues with documented decisions and acceptance criteria, turning archaeology into a lookup.

#### Three Consumers

**git-zhi core** uses lineage for:

- **Context enrichment** on `issue show` — the primary use case. Workers get upstream context automatically.
- **Targeted verification** — `git zhi verify` can prioritize re-running ACs from upstream issues when downstream modifications touch their code.
- **Parallelization refinement** — even when two issues have no declared dependency and no explicit `context.paths` overlap, historical lineage data can flag files with high coupling as risk areas.

**Sanbao** uses lineage for:

- **Coupling analysis** — identifying files modified by many issues as coordination hotspots
- **Change coupling trends** — files that always change together across issues (even when not in the same `context.paths`)

**Crochet** uses lineage for:

- **Decomposition intelligence** — when `crochet:refinement` generates issues for a new milestone, lineage from the previous milestone informs which files have deep history and may need extra context
- **Postmortem analysis** — `crochet:postmortem` can identify high-lineage files as candidates for refactoring

#### Implementation Note

The lineage graph is a significant addition — a second DAG alongside the dependency graph, with different semantics and different construction. The dependency graph is declared and enforced; the lineage graph is observed and advisory. The dependency graph is acyclic by invariant; the lineage graph is typically acyclic because changes flow forward in time (UUIDv7 ordering), but the issue-level projection may contain cycles when multiple issues modify overlapping regions of the same file. Cycles in the lineage graph are not errors — they indicate high coupling and are valuable signals for parallelization risk and refactoring candidates.

The `git blame` computation is fast for the expected scale (tens to low hundreds of issues, session-sized changes). For large repositories with deep history, the blame can be scoped to the lines within the issue’s `context.paths` rather than the entire file, keeping it bounded.

### Planning Telemetry

v0.2 adds forecast accuracy tracking to the existing telemetry. After each milestone completes, the system records predicted versus actual completion time. Over multiple milestones, forecast accuracy itself becomes a measurable, improvable metric.

The full set of planning-relevant indicators in v0.2:

## git-zhi-verify Plugin

A standalone Go binary installed as `git-zhi-verify`, invocable as `git zhi verify`.

### Behavior

1. Reads all done issues in the specified milestone (or current milestone if none specified)
1. Parses backtick-delimited commands from both `### Positive Scenarios` and `### Negative Scenarios` under `## Acceptance Criteria`
1. Orders issues for execution by regression likelihood:
- **First**: issues whose `observed_paths` overlap with files changed since the issue was marked done (most likely to have regressed)
- **Second**: issues with lineage connections to recently completed issues (coupling-based risk)
- **Third**: all remaining issues
1. Executes each command in the repository root, subject to timeout (see Execution Safety)
1. Reports pass/fail per issue, per scenario subsection

The `--fail-fast` flag stops on the first regression, useful for quick checks. The default runs all commands and reports a full summary.

### Output

```
$ git zhi verify v0.1

  Positive:
    ✓ go test -run TestLexer_Tokens -v
    ✓ go test -run TestLexer_Errors -v
  Negative:
    ✓ go test -run TestLexer_InvalidUTF8 -v
    ✓ go test -run TestLexer_EmptyInput -v

019444a2  Parse basic declarations
  Positive:
    ✓ go test -run TestParse_SubDecl -v
    ✗ go test -run TestParse_MultiLine -v          ← REGRESSION
  Negative:
    ✓ go test -run TestParse_MalformedDecl -v

019444a3  Parse signatures
  Positive:
    ✓ go test -run TestSignature_Positional -v
  Negative:
    ✗ go test -run TestSignature_CircularDefault -v  ← REGRESSION

v0.1: 9/11 acceptance criteria passing
      Positive: 5/6 | Negative: 4/5

```

### JSON Output

`git zhi verify v0.1 --format json` returns structured results consumable by agents and the sanbao observatory.

### Exit Code

- 0: all criteria pass
- 1: one or more regressions detected

This allows `git zhi verify` to be used as a gate in scripts, CI, and the milestone completion flow.

### Execution Safety

`git zhi verify` runs shell commands parsed from markdown. In a shared repository, malicious or careless acceptance criteria could execute destructive commands. Mitigations:

- **Timeout**: each command has a default timeout of 5 minutes, configurable via `git config zhi.verify.timeout <seconds>`. Commands exceeding the timeout are killed and reported as failures.
- **Dry-run mode**: `git zhi verify --dry-run` lists commands that would be executed without running them. Useful for reviewing AC commands in unfamiliar repos before trusting them.
- **No implicit privileges**: verify runs commands as the current user with no privilege escalation. It does not modify the working tree, create files, or change git state.
- **CI isolation**: in CI environments, verify runs inside whatever sandboxing the CI platform provides (containers, VMs). The verify plugin itself does not provide sandboxing — it relies on the execution environment.

For solo and small-team use (v0.2 target), the threat model is the same as running `make test` — you’re executing code you wrote or reviewed. Full command sandboxing (allowlists, capability restrictions) is a consideration for v0.4 multiplayer when untrusted contributors may add acceptance criteria.

## git-zhi-sanbao Plugin — Observatory

A standalone Go binary installed as `git-zhi-sanbao`, invocable as `git zhi sanbao`. Computes engineering health metrics from `refs/zhi/` data. Not required for scheduling — purely observational. Independent release cadence.

### DORA Metrics

DORA metrics traditionally measure commit-to-production. Zhi doesn’t have a deployment pipeline, so it measures the same signals through the issue lifecycle instead. For projects where “issue done” closely corresponds to “merged to main,” these are good approximations. For projects with separate deployment pipelines, they measure development throughput, not delivery throughput.

|Metric                     |Derivation                                                          |
|---------------------------|--------------------------------------------------------------------|
|Lead time (issue)          |Issue `created` timestamp to `done` state transition                |
|Cycle time (issue)         |`start` state transition to `done` state transition                 |
|Change failure rate (issue)|Issues transitioned done→reopened as percentage of total completions|
|Completion frequency       |Issues completed per calendar period (overlaps with zhi’s speed)    |

### SPACE Metrics

|Dimension    |Metric                   |Derivation                                                                    |
|-------------|-------------------------|------------------------------------------------------------------------------|
|Performance  |Milestone completion rate|Milestones completed on/before due vs after                                   |
|Performance  |Forecast accuracy        |Predicted vs actual, from zhi telemetry                                       |
|Activity     |Commits per issue (MPG)  |From zhi telemetry                                                            |
|Activity     |Session count per issue  |Session bookmark count on issue refs                                          |
|Communication|Agent autonomy rate      |Issues completed with no human state-change interventions                     |
|Communication|Review cycle count       |Number of commits between first done attempt and final done (rework indicator)|
|Efficiency   |Time-in-chain            |From zhi telemetry                                                            |
|Efficiency   |Shadow work ratio        |From zhi telemetry                                                            |
|Satisfaction |Not directly measurable  |Out of scope for CLI tooling — survey-based                                   |

### CALMS Indicators

|-----------|--------------------------|------------------------------------------------|

|Sharing    |Postmortem completion rate|Milestones with attached postmortem vs without  |

### Commit Sentiment Analysis

The sanbao plugin performs lexicon-based sentiment analysis on commit messages using VADER (Valence Aware Dictionary and sEntiment Reasoner). VADER is rule-based and deterministic — no ML model, no LLM. It was designed for short informal text and works well on commit messages, scoring each message on positive, negative, neutral, and compound polarity.

**Caveat:** Commit message sentiment is a weak signal, not a diagnostic. Commit messages are terse, technical, and often neutral. Words like “fix”, “refactor”, and “hack” skew negative in VADER even when they reflect normal development. Sentiment data should be consumed as one input among many in the postmortem — a flag that prompts investigation, not a conclusion. A sustained negative trajectory warrants a look; a single negative commit means nothing.

VADER understands context that keyword detection misses. “Fixed the hack” and “this is a hack” have very different sentiments — a keyword scanner flags both, VADER distinguishes them. “Not sure this is right but it passes” scores as uncertain/negative; “clean refactor of signature parsing” scores positive; “ugh, hacking around this for now” scores strongly negative.

**Per-issue sentiment trajectory:**

Over an issue’s lifetime, the sequence of commit sentiment scores tells a story. Starts positive, dips negative mid-issue, recovers — that’s a normal struggle. Starts neutral, goes negative, stays negative — that’s a worker in trouble. Sanbao tracks the trajectory and flags anomalous patterns:

```
019444a1  Implement lexer
  Sentiment: 0.42 → 0.38 → 0.15 → 0.41 → 0.55
  Trajectory: normal (dip and recovery)

019444a4  Error recovery
  Sentiment: 0.30 → -0.12 → -0.35 → -0.28 → -0.15
  Trajectory: ⚠ sustained negative — worker may be struggling
```

**Per-milestone sentiment summary:**

Aggregate sentiment across all issues in a milestone provides a health signal that’s richer than throughput metrics alone. A milestone that shipped on time but with declining sentiment across issues may indicate accumulating frustration or technical debt that doesn’t show up in speed or MPG.

**Metrics derived from commit analysis:**

|Metric                           |Derivation                                                                           |
|---------------------------------|-------------------------------------------------------------------------------------|
|Session abandonment rate         |Issues with `start` state but no subsequent `done` or `pause`                        |
|AC completion ratio at done      |Checked vs unchecked criteria when issue marked done                                 |
|Positive vs negative AC pass rate|`git zhi verify` results by subsection over time                                     |
|Mean commit sentiment            |Average VADER compound score across commits per issue                                |
|Sentiment trajectory             |Compound score trend over an issue’s commit sequence                                 |
|Sentiment anomalies              |Issues with sustained negative sentiment (compound < -0.1 for 3+ consecutive commits)|

### Issue Difficulty (Derived)

Sanbao derives a difficulty signal per issue from existing metrics — no new fields required. High MPG (many commits), long cycle time, negative sentiment trajectory, and reopens all indicate a harder-than-expected issue. Sanbao combines these into a normalized difficulty score:

|Factor                 |Weight Direction      |
|-----------------------|----------------------|
|MPG (commits per issue)|Higher = harder       |
|Cycle time             |Longer = harder       |
|Reopen count           |Any reopen = harder   |
|Mean sentiment         |Lower = harder        |
|Session count          |More sessions = harder|

The difficulty score is not prescriptive — it doesn’t change scheduling or gating. It feeds two consumers: `crochet:postmortem` uses it to identify which issues were unexpectedly hard and why, and `crochet:refinement` can read historical difficulty data from past milestones to improve future issue sizing (“issues touching the parser averaged 2.3× difficulty — consider thinner slices”).

### Code Complexity

The sanbao plugin provides complexity analysis at two levels:

**Language-agnostic (always available, no config):**

- **File churn**: how many times each file was modified across issues in a milestone
- **File size**: lines of code per file at milestone start vs completion
- **Churn × size hotspots**: large files with high churn — the strongest language-agnostic predictor of defect-prone code
- **Change coupling**: files that always change together (derived from commit co-occurrence)
- **Indentation depth statistics**: average and max nesting depth per file — correlates with cyclomatic complexity

**Language-specific (via LSP, when configured):**

When a language server is declared in git config, sanbao connects via the Language Server Protocol and requests diagnostics, symbol information, and complexity data for files touched in a milestone.

```bash
git config zhi.lsp.go "gopls"
git config zhi.lsp.perl "PLS"
git config zhi.lsp.typescript "typescript-language-server"
```

Sanbao speaks the LSP JSON-RPC protocol — it doesn’t parse any language itself. The language server provides cyclomatic complexity, symbol resolution, dead code detection, type-level diagnostics, and whatever else the server exposes. Files with no configured language server still get the churn-based analysis. LSP enriches, it doesn’t replace.

This avoids building per-language tooling into sanbao. One protocol, all languages. The language server is already on the developer’s machine if they use an editor.

## git-zhi-docs Plugin — Documentation Health

A standalone Go binary installed as `git-zhi-docs`, invocable as `git zhi docs`. Scaffolds and validates a canonical `docs/` directory structure, monitors documentation health relative to code churn, and tracks stability metadata.

### Canonical Directory Structure

`git zhi docs init` creates:

```
CONTRIBUTING.md              # Entry point — hub linking to everything below
docs/
├── plans/                   # Specs and design docs from brainstorming
├── decisions/               # ADRs (MADR convention, numbered sequentially)
├── contributing/            # Extended contributor docs
│   ├── coding-conventions.md
│   └── development-workflow.md
├── guides/                  # How-to guides for project capabilities
├── architecture/            # Architecture overviews
└── reference/               # Technical reference
```

If `CONTRIBUTING.md` already exists, `git zhi docs init` adds missing directories and proposes link additions to the existing file. ADRs use the MADR (Markdown Architectural Decision Records) format. ADR numbering is sequential; old decisions are never deleted, only superseded.

The `docs/plans/` directory is where `crochet:refinement` specs land (the brainstorming output) and where postmortems can be promoted if they contain broadly useful lessons.

### Documentation Stability Metadata

Docs can carry stability and coverage metadata in YAML frontmatter:

```yaml
---
stability: 2              # 0: deprecated, 1: experimental, 2: stable
covers:
  - internal/parser/
  - internal/issue/sections.go
---
```

The `stability` field follows Node.js’s convention: deprecated (flagged for removal), experimental (expected to change), stable (reliable). The `covers` field declares which code paths the document describes — used for churn-relative staleness detection.

### Churn-Relative Documentation Health

Fixed calendar thresholds for documentation freshness are misleading. A doc about the parser that hasn’t been updated in 60 days is fine if the parser hasn’t changed — but stale if the parser had 20 commits across 4 issues in that period.

`git zhi docs health` measures staleness relative to code activity in the areas each document covers. For each doc with a `covers` field (or with inferred file references from content), it computes the code churn since the doc was last modified and reports a drift level:

```
$ git zhi docs health

docs/architecture/parser-design.md
  Covers: internal/parser/
  Doc modified: 2026-02-15 | Code churn since: 34 commits, 5 issues
  Drift: HIGH — doc significantly behind code

docs/architecture/system-overview.md
  Covers: cmd/, internal/cli/
  Doc modified: 2026-03-01 | Code churn since: 3 commits, 1 issue
  Drift: LOW — doc roughly current

docs/guides/getting-started.md
  Covers: cmd/git-zhi/main.go, internal/cli/root.go
  Doc modified: 2026-01-15 | Code churn since: 0 commits
  Drift: NONE — code hasn't changed

docs/decisions/0003-use-go-git.md
  ADR — exempt from staleness checks
  Status: accepted

Coverage:
  ⚠ Milestone v0.1 completed with no ADRs recorded
  ⚠ internal/telemetry/ has no architecture doc
  ✓ 4/4 guides reference valid file paths

Summary: 1 high drift, 1 low drift, 0 broken references, 2 coverage gaps
```

Stability level modulates the drift sensitivity — experimental docs are expected to change more frequently than stable docs, so the same code churn produces a higher drift score for an experimental doc than a stable one. ADRs and postmortems are append-only records and skip staleness checks entirely.

### Coverage Gap Detection

`git zhi docs health` also detects:

- **Missing architecture docs**: packages or major directories with no corresponding document in `docs/architecture/`
- **Orphaned references**: docs that reference files or paths that no longer exist in the codebase
- **ADR gaps**: milestones completed without any decision records (configurable — some milestones don’t involve significant decisions)
- **Guide gaps**: new CLI commands or user-facing features with no corresponding guide

### Validation

`git zhi docs check` validates structural consistency:

- All files in `docs/` are reachable from CONTRIBUTING.md links
- ADR numbering is sequential with no gaps
- All `covers` paths in frontmatter resolve to existing files or directories
- No dead links between documents

### JSON Output

`git zhi docs health --format json` exposes health data for consumption by sanbao (documentation health as an engineering metric), `crochet:postmortem` (which docs drifted during the milestone), and `crochet:refinement` (which existing docs might be affected by planned work).

## Crochet — Claude Code Plugin

Crochet is a Claude Code plugin — skills and prompts, not a binary. It requires LLM access and integrates with the Obra Superpowers workflow. All interaction with chain state goes through `git zhi` CLI commands: `git zhi milestone add` to create milestones, `git zhi issue add` to create issues (including batch creation via stdin), `git zhi list --format json` to read chain state, `git zhi milestone show --format json` to read milestone data. Crochet never accesses `refs/zhi/` directly.

### crochet:refinement

Replaces `superpowers:writing-plans`. Takes a spec (output of `superpowers:brainstorming`) and produces an executable chain.

**Trigger:** Approved design spec exists, user says “go” or “plan this” or “break this down.”

**Agent roles within refinement:**

1. **Architect agent**: reads the spec plus codebase, produces milestone context (architecture overview, file structure, design rationale, resolution command)
1. **Decomposer agent**: breaks the spec into issues with dependencies, structured context (`paths`, `commands`, `entrypoints`), steps (RED-GREEN-COMMIT choreography), and positive acceptance criteria
1. **SQE agent**: reads each issue’s positive acceptance criteria and the spec, generates negative scenarios — boundary conditions, error paths, race conditions, invalid inputs, state corruption. The SQE agent never sees implementation code. It only sees specs and acceptance criteria, ensuring test independence.
1. **Technical writer agent**: reads the spec, the existing `docs/` contents, and `git zhi docs health --format json` to determine documentation impact. Produces two kinds of output:
- **Doc update steps on code issues**: when an issue changes code that’s covered by existing documentation, the tech writer adds a step to that issue — “update `docs/architecture/parser-design.md` to reflect the new signature node type.” The doc update is part of the definition of done for that issue.
- **Standalone documentation issues**: for new capabilities that need new guides, significant design decisions that warrant ADRs, or architecture overviews for new subsystems. These are real issues in the chain with their own dependencies (a parser usage guide depends on the parser issues being done), acceptance criteria, and context pointing at `docs/`.

**Lazy initialization:**

On first run in a repository, `crochet:refinement` inspects existing project structure and bootstraps:

- **CONTRIBUTING.md**: tech stack, build/test commands, architecture overview, coding conventions, quality tool declarations. If CONTRIBUTING.md already exists, Crochet proposes additions rather than overwriting.
- **CLAUDE.md**: agent-specific directives, pointer to CONTRIBUTING.md. If CLAUDE.md already exists, ensures it references CONTRIBUTING.md.

On subsequent runs, Crochet checks existing files and proposes updates only if the new spec introduces new conventions, dependencies, or architectural patterns.

**Output:**

### crochet:postmortem

**Mandatory at milestone completion.** A process retrospective, not a bug report or documentation audit. Modeled on Esther Derby’s retrospective framework: what worked, what didn’t, what puzzles us, and what will we do differently.

The postmortem exists to monitor **process health** and recommend **process improvements**. Product quality is handled by verify (regressions), sanbao (metrics), and docs health (documentation drift). The postmortem asks: how is our *way of working* holding up, and what should change?

**Trigger:** All issues done, resolution command passed, verify clean. The agent (or orchestrator) invokes `crochet:postmortem` before `git zhi milestone edit --state complete`.

**Inputs (all accessed via `git zhi` CLI):**

- All issues in the milestone via `git zhi issue list --milestone v0.1 --format json` (state transitions, session data, lineage)
- Milestone telemetry via `git zhi milestone show v0.1 --format json` (speed, MPG, buffer burn history)
- `git zhi verify v0.1 --format json` results (which AC passed/failed)
- `git zhi docs health --format json` results (which docs drifted during the milestone)
- Commit messages via `git log` on session SHA ranges
- Sanbao metrics if available via `git zhi sanbao report v0.1 --format json` (DORA, complexity, sentiment)

**Produces a process retrospective structured around four questions:**

1. **What worked well?**
- Which process conventions produced clean execution? (Issues with low commit counts, no reopens, ACs passing first time)
- Was the decomposition accurate? (Issues that didn’t need splitting, merging, or cancellation)
- Where did parallelization succeed? (Workers that operated independently without merge friction)
1. **What didn’t work?**
- Where did workers struggle? (High commit counts, negative sentiment trajectories, reopened issues, session abandonment)
- Where was the decomposition wrong? (Issues that were split or merged mid-milestone, undeclared coupling discovered via lineage)
- Where did the forecast miss? (Predicted vs actual — and *why* it was off, not just that it was)
1. **What puzzles us?**
- Unexpected patterns in the data (issues that were easy on paper but hard in practice, or vice versa)
- Anomalous telemetry (speed that changed mid-milestone, sudden MPG spikes)
- Lineage surprises (coupling that nobody anticipated)
1. **What will we do differently?**
- Concrete process recommendations: “Issues touching the parser averaged 12 commits versus 4 for other packages — consider thinner slices in parser-heavy milestones”
- Decomposition improvements: “Three issues had undeclared coupling through `config.go` — the decomposer should flag shared config files as coordination risks”
- Convention changes: “The SQE agent’s negative scenarios caught 2 regressions — maintain this practice” or “Issue steps were too prescriptive and the agent had to deviate — use lighter steps”
- Tooling observations: “The frontmatter library returns `[]byte` not `io.Reader` — add to coding conventions”

The postmortem deliberately does **not** propose documentation updates directly. That’s Scribe’s concern (see Related Projects). The postmortem surfaces process insights; other tools and humans decide which insights warrant documentation changes.

**Storage:**

Crochet generates the postmortem content and attaches it to the milestone via `git zhi milestone edit v0.1 --postmortem` (piping the document via stdin, same pattern as `issue add`). The postmortem is stored on the milestone ref as `postmortem.md`, viewable via:

```bash
git zhi milestone show v0.1 --postmortem
git show refs/zhi/_/milestones/v0.1:postmortem.md
```

Future runs of `crochet:refinement` read past postmortems via `git zhi milestone show --format json` to avoid repeating process mistakes. The system accumulates institutional knowledge about *how to work*, not just what was built.

## Workflows

### Per-Issue Workflow

Whether the worker is you, a colleague, or a coding agent, the flow is the same:

```
Worker picks up issue (git zhi issue show --format json, or git zhi next)
  → Absorbs context:
      CONTRIBUTING.md (repo conventions, build/test commands)
      Milestone context (architecture, file structure)
      Issue context (paths, commands, entrypoints)
  → Creates worktree/branch
  → Works through ## Steps with TDD discipline
  → Passes all Positive Scenarios
  → Passes all Negative Scenarios
  → Code review (self-review for humans, two-stage for agents)
  → Merge/PR
  → git zhi issue edit <id> --state done
  → HEAD advances to next issue on critical chain
```

When using the Obra Superpowers workflow, agents use `superpowers:using-git-worktrees`, `superpowers:test-driven-development`, `superpowers:finishing-a-development-branch`, and two-stage code review (spec compliance, then code quality). Humans follow the same structure at their discretion.

### Per-Milestone Workflow

```
All issues done (or cancelled with scope cuts)
  → git zhi milestone edit v0.1 --resolve
      Executes the resolution command (integration gate)
      Fails fast if resolution command returns non-zero
  → git zhi verify v0.1
      Runs all AC commands across all done issues
      Reports regressions
      Fails if any regressions detected
  → crochet:postmortem v0.1
      Reads chain data via git zhi CLI, generates narrative + proposals
      Attaches postmortem via git zhi milestone edit --postmortem
      Proposes CONTRIBUTING.md updates for human review
  → git zhi milestone edit v0.1 --state complete
      Gated: refuses if resolution or verify failed
      Records completion timestamp
      Locks milestone (no further issue additions)
```

### Parallel Work Coordination

When you have more than one worker available — you’re working on one issue while an agent handles another, or two developers are working simultaneously — zhi’s parallelization analysis guides assignment:

```
developer (or orchestrator script):
  workers = available_worker_count
  
  loop:
    ready = git zhi list --ready --format json
    if ready is empty and all issues done:
      → run milestone completion workflow
      → stop
    
    # Check for path-safe parallel assignments
    assignments = select_non_overlapping(ready, workers)
    
    for each (worker, issue) in assignments:
      worker starts issue in their own worktree
    
    wait for any worker to complete
    # HEAD advances, new issues may become ready
    # Loop continues with updated ready set
```

The `select_non_overlapping` step uses zhi’s path overlap data to avoid assigning issues with shared `context.paths` to concurrent workers. Issues that overlap are sequenced; issues that don’t overlap are parallelized. A solo developer with one agent helper typically sees a ready set of 1–3 issues — enough to keep both productive without coordination overhead spiraling.

## Convention Changes

### CONTRIBUTING.md as Hub, docs/ as Substance

CONTRIBUTING.md becomes a lightweight entry point — a hub that links to deeper documentation in `docs/`. Following the pattern established by Kubernetes, Django, and Rust, CONTRIBUTING.md contains only what a contributor needs in the first five minutes: how to file a bug, how to submit a PR, and a “Short Links to Important Resources” section that indexes every document in `docs/`. It does not contain the full text of coding conventions, architecture overviews, or workflow guides — those live in their respective `docs/` subdirectories.

GitHub surfaces CONTRIBUTING.md automatically in the repo overview and when contributors open issues or PRs. This makes it the natural front door for both humans and agents. The canonical directory structure is created and maintained by `git zhi docs init` and `git zhi docs check`.

CONTRIBUTING.md links to:

- `docs/contributing/coding-conventions.md` — style, patterns, quality tool declarations
- `docs/contributing/development-workflow.md` — how to pick up and complete issues
- `docs/architecture/` — system overviews, package-level docs
- `docs/decisions/` — ADRs capturing significant design choices
- `docs/guides/` — how-to guides for project capabilities
- `docs/reference/` — technical reference material
- `docs/plans/` — specs from brainstorming, design documents

### CLAUDE.md Becomes a Thin Pointer

CLAUDE.md retains agent-specific directives but delegates project knowledge to CONTRIBUTING.md:

```markdown
# CLAUDE.md

Read CONTRIBUTING.md for project conventions, build commands, test
commands, and architecture.

## Agent Directives

- Use superpowers:using-git-worktrees for all implementation work
- Use crochet:refinement for PRD decomposition (replaces writing-plans)
- Use crochet:postmortem at milestone completion (mandatory)
- Run git zhi verify before marking milestones complete
- Check git zhi list --ready for parallelization guidance
```

### Living Documentation

The `docs/` directory contains living documents that evolve with the codebase. `git zhi docs health` monitors their freshness relative to code churn (see git-zhi-docs Plugin section). Postmortems surface process insights that may warrant documentation updates, but the postmortem itself does not propose specific edits — documentation generation and maintenance is the concern of the technical writer agent (in `crochet:refinement`) and, in the future, the Scribe project (see Related Projects).

## Milestone Format (v0.2)

Complete example showing all v0.2 additions:

```yaml
name: "v0.1"

due: "2026-04-15"
resolution: "make integration-test"

---

## Context

Single Go binary at cmd/git-zhi/main.go. Cobra root command with
subcommand groups (issue, milestone, top-level list/config/next).
Internal packages under internal/ own domain logic.

## File Structure

  cmd/git-zhi/main.go
  internal/cli/root.go, issue.go, milestone.go, chain.go
  internal/storage/store.go
  internal/issue/issue.go, sections.go
  internal/milestone/milestone.go
  internal/graph/graph.go
  internal/telemetry/telemetry.go
  internal/config/config.go
  internal/resolve/resolve.go

## Design Rationale

Issues are ordered so that storage is built first (no deps),
then domain types, then CLI wiring, then integration verification.
The critical chain runs through storage → issue → CLI → integration.
Off-chain parallelism exists between graph, telemetry, config, and
resolve packages.
```

## Implementation Phases

v0.2 is itself decomposable into sequential deliverables:

### Phase 1: Data Model Enrichment

- Milestone body (markdown body alongside YAML frontmatter)
- Milestone lifecycle (state: open → completed, completed timestamp)
- Issue `## Steps` section (parsing in `ParseSections`)
- Issue AC subsections (`### Positive Scenarios` / `### Negative Scenarios`)
- Urgency field on issues
- Issue state machine: reopened state, transition log with actor identity
- Worker identity on state transitions (actor field, `type:identifier` format)
- `observed_paths` recording at issue completion (`git diff --name-only start..end`)
- JSON output includes milestone context with issue show

### Phase 2: Milestone Completion Gates

- Resolution command execution (`git zhi milestone edit --resolve`)
- Gate enforcement on `--state complete`

### Phase 3: git-zhi-verify

- AC backtick command parser (both subsections)
- Command executor with timeout and error handling
- Prioritized execution order (observed_paths overlap → lineage → remaining)
- `--fail-fast` flag, `--dry-run` flag
- Human and JSON output formatters
- Exit code semantics

### Phase 4: Parallelization

- Ready set computation (already implicit in graph — make it explicit)
- `context.paths` + `observed_paths` union for overlap detection
- Multi-worker WIP semantics (WIP = 1 per worker, HEAD resolves per caller)
- `--ready` flag on `git zhi list`
- `--workers N` forecast on `git zhi milestone show`
- Coordination tax estimation (initially heuristic, refined from telemetry)

### Phase 5: Lineage Tracking

- Blame-to-issue mapping: trace modified lines back to originating issue sessions
- Read-time lineage computation on `issue show` (human and JSON output)
- Lineage-informed verification targeting in `git zhi verify`
- Lineage data in parallelization risk assessment

### Phase 6: Planning Telemetry

- Forecast accuracy tracking (predicted vs actual per milestone)
- Parallel efficiency tracking (actual vs theoretical)

### Phase 7: git-zhi-sanbao (separate deliverable)

- DORA metric computation (issue-level proxies)
- SPACE metric computation
- CALMS indicators
- VADER-based commit sentiment analysis (per-issue trajectory, per-milestone summary, anomaly detection)
- Issue difficulty derivation (composite signal from MPG, cycle time, reopens, sentiment, session count)
- Code complexity (language-agnostic: churn, file size, indentation depth, change coupling)
- LSP integration for language-specific metrics (cyclomatic complexity, diagnostics, dead code detection) via git config declarations
- Lineage-based coupling analysis and trend reporting
- Human and JSON output

### Phase 8: git-zhi-docs (separate deliverable)

- `git zhi docs init` — scaffold canonical `docs/` directory structure
- `git zhi docs check` — validate CONTRIBUTING.md index matches `docs/` contents, detect dead links, verify ADR numbering
- `git zhi docs health` — churn-relative staleness detection, stability metadata tracking, coverage gap detection
- Human and JSON output (JSON consumed by sanbao, crochet:postmortem, crochet:refinement)

### Phase 9: Crochet (separate deliverable, Claude Code plugin)

- `crochet:refinement` skill (architect + decomposer + SQE + technical writer agents)
- Technical writer agent: doc update steps on code issues, standalone doc issues for guides/ADRs
- CONTRIBUTING.md / CLAUDE.md lazy initialization (calls `git zhi docs init` for scaffolding)
- `crochet:postmortem` skill (process retrospective, mandatory at milestone completion)

## Success Criteria

v0.2 is successful if:

1. A solo developer can hand off an issue to a coding agent and trust the result — the quality gates (AC, code review, verify) catch problems before they integrate
1. A developer working alongside one or two agents can complete a milestone faster than solo, with `--workers` forecast accurately predicting the speedup
1. Negative acceptance criteria catch at least one bug per milestone that positive scenarios would have missed
1. `git zhi verify` catches regressions before milestone completion
1. Parallelization recommendations accurately predict merge-conflict-free parallel execution
1. Lineage tracking surfaces relevant upstream context on `issue show`, eliminating manual `git blame` archaeology for workers picking up unfamiliar code
1. Forecast accuracy improves across successive milestones as telemetry accumulates
1. `crochet:postmortem` produces actionable process recommendations that measurably improve subsequent milestone execution (better issue sizing, more accurate decomposition, fewer surprises)
1. DORA metrics are computable from `refs/zhi/` data without any manual instrumentation
1. The same workflow serves a solo developer, a developer with agent helpers, and a small human team without requiring different configurations
1. `git zhi docs health` detects documentation drift from code churn, and the technical writer agent in `crochet:refinement` keeps docs in the chain alongside code

## Future Considerations

Beyond v0.2, planned for future versions:

1. **Mutation testing** — Verify test quality by mutating code and checking whether tests catch the mutations. May become a sanbao plugin or a standalone `git-zhi-*` plugin. Addresses the test theater problem from a different angle than the SQE agent — the SQE agent generates adversarial specs *before* code exists, mutation testing verifies test effectiveness *after* code exists.
1. **LLM-assisted narrative analysis** — VADER provides per-commit polarity scores. A future Crochet skill (`crochet:analyze`) could go deeper — reading commit sequences as a narrative and producing a qualitative health assessment that distinguishes between human frustration signals and agent hedging patterns, identifies where workers deviated from the plan and why, and summarizes the “story” of a struggling issue in natural language for the postmortem.
1. **Scribe — Documentation Intelligence.** A planned documentation generation and maintenance system, likely a standalone Claude Code plugin. Where Crochet manages *work* (issues, milestones, chains), Scribe would manage *knowledge* (decisions, guides, architecture docs, conventions). Scribe’s value proposition — generating and maintaining living documentation from project activity — isn’t coupled to zhi. Any project with a git repo and a `docs/` directory could use it. Zhi data makes it *better* (milestones give it narrative arc, issues give it decision context, postmortems give it process insights), but it doesn’t *require* zhi. Potential skills: `scribe:decision` (MADR from design discussions), `scribe:guide` (how-to guides after new capabilities), `scribe:architecture` (updates based on milestone changes), `scribe:index` (regenerates CONTRIBUTING.md links). The technical writer agent in `crochet:refinement` handles documentation *planning*; Scribe would handle documentation *generation*.

### Static Plan Files

Plan files under `docs/superpowers/plans/` are superseded by the zhi chain. Existing plan files remain as historical artifacts. New work uses `crochet:refinement` to produce issues directly.

The plan file header (goal, architecture, file structure) migrates to the milestone body. The plan file tasks (steps, code, verification) migrate to issue `## Steps` and `## Acceptance Criteria`. The plan file preamble (tech stack, conventions) lives in CONTRIBUTING.md.
