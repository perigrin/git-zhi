# v0.3.3 PRD — Batch-Add DAG Awareness and Issue Body Editing

## Overview

v0.3.3 fixes two feature gaps surfaced by the v0.3.2 fitness assessment.
Both are quality-of-life improvements to the issue management interface
that were identified during real use of the stack to build the
perl-development plugin.

This release also serves as the test bed for three v0.3.x components that
were not exercised during v0.3.2: Ralph Loop (sustained iterative
development), sanbao telemetry (MPG, speed, fever under real coding load),
and postmortem (milestone retrospective).

## Problem Statement

### Batch-add creates false sequential dependencies

`git zhi issue add` with multiple issues from stdin chains them
sequentially — each issue blocks the next. This is the wrong default.
Most batch-created issues are independent work items, not sequential steps.
During the v0.3.2 assessment, every batch-add required manual dependency
correction: 10 false sequential dependencies had to be removed and 12
fan-in dependencies added in their place. This was the most time-consuming
fix in M2 (refinement correction).

The DAG already knows which issues are independent — the absence of declared
dependencies is the signal. The tool should respect that signal instead of
inventing dependencies that don't exist.

### Issue body editing requires JSON pipe

Updating an issue's body requires constructing a JSON object with the
`issue_id` and `body` fields and piping it through `--batch`. This is
workable for programmatic use but hostile for interactive editing. During
v0.3.2, every issue body update required a Python one-liner to produce
valid JSON. A direct `--body` flag with stdin/editor support would match
the ergonomics of `git commit`.

## Changes

### 1. Batch-add defaults to parallel

**Current behavior:** Multiple issues from stdin are chained sequentially.
Issue N blocks issue N+1.

**New behavior:** Multiple issues from stdin are created as independent
(unblocked) issues. Sequential chaining only happens when the user
explicitly declares dependencies using `--after` or `--before` in the
YAML frontmatter.

**Breaking change:** Yes. The implicit sequential chaining is removed.
No deprecation path — no external consumers rely on the implicit behavior.

**Input format change:** The YAML frontmatter for batch issues gains
optional `after` and `before` fields:

```yaml
---
title: "First task"
---

First body.

---
title: "Second task"
after: "First task"
---

Second body, explicitly depends on first.

---
title: "Third task"
---

Third body, independent of both.
```

The `after` field accepts an exact title match (within the current batch)
or an existing issue ref (UUID prefix). Resolution order:

1. Exact title match against other issues in the same batch
2. If no batch match, resolve as issue ref against existing issues
3. If multiple batch titles match, error
4. If no match at all, error

When `after` is present, the new issue is blocked by the resolved issue.
When absent, the issue has no dependencies.

The `before` field is the inverse — the resolved issue becomes blocked
by the new issue. Same resolution rules apply.

**Batch-add output change:** The current output says "chained sequentially."
The new output should report dependency structure:

```
Created 3 issues:
  019d0508  First task
  019d0508  Second task (after: First task)
  019d0508  Third task
```

### 2. Issue edit --body

**New flag:** `--body` on `git zhi issue edit`.

**Behavior:**

1. If stdin is not a TTY (piped input), read the new body from stdin.
2. If stdin is a TTY (interactive), resolve the editor using
   `git var GIT_EDITOR` (which respects `$GIT_EDITOR`, `$VISUAL`,
   `$EDITOR`, then falls back to `vi`). Open the editor with the
   current issue body pre-populated in a temp file. On editor exit,
   replace the body with the file contents.
3. If the editor contents are unchanged or empty, abort with no changes.

**Interaction with existing flags:** `--body` is independent of other
`issue edit` flags. It can be combined with `--state`, `--label`, etc.
in a single command.

**Example usage:**

```bash
# Pipe new body
echo "Updated acceptance criteria" | git zhi issue edit abc123 --body

# Interactive editor
git zhi issue edit abc123 --body
# Opens $EDITOR with current body
```

## Design Principles

1. **Explicit over implicit.** Dependencies are declared, not inferred
   from input order.
2. **Match git ergonomics.** `--body` follows the `git commit` pattern:
   stdin or editor.
3. **Backward compatibility where possible.** Single-issue `issue add`
   is unchanged. Only multi-issue batch behavior changes.

## Test Strategy

TDD in Go. Real on-disk git repos via `t.TempDir()`. No mocks.

### Batch-add tests

- Multi-issue add without `after`/`before`: all issues have empty
  `blocked_by` and `blocks`
- Multi-issue add with `after`: correct dependency created
- Multi-issue add with `before`: correct inverse dependency created
- Mixed: some issues with deps, some without
- `after` referencing a title that doesn't exist: error
- `after` with duplicate batch title match: error
- `after` referencing an existing issue by UUID ref: correct dependency
- Single-issue add: unchanged behavior (no deps)

### Issue edit --body tests

- Pipe new body via stdin: body replaced
- Empty stdin (simulated): body unchanged
- `--body` combined with `--state`: both applied
- Body with YAML-like content (frontmatter markers): correctly stored
  as body, not parsed as frontmatter
- `$EDITOR` integration: set `$EDITOR` to a script that modifies the
  temp file, verify body is updated
- `$EDITOR` exits non-zero: body unchanged, edit aborted

## Non-Goals

- Batch-add with automatic dependency inference from content analysis
- Interactive dependency selection during batch-add
- Rich text or markdown rendering in `--body` editor mode
- `--body` on `issue add` (it already reads body from stdin)
