# Agentic Team Orchestration for git-zhi

## Specification: Fractal Work Management with Throughput Accounting

### Context

git-zhi currently tracks issues and milestones within individual repositories. This spec extends the model upward to projects and portfolios, adds throughput accounting (Goldratt's Theory of Constraints), and defines how human teams and agentic teams interact with the system using the same primitives. The immediate use case is managing a team of 11 humans with varying agent adoption across a portfolio of projects spanning multiple repositories.

---

## 1. Fractal Hierarchy

### 1.1 Entity Definitions

| Entity | Contains | Scope | Has Goal | Has TA |
|---|---|---|---|---|
| **Issue** | — (leaf node) | Always within one repo | Acceptance criteria | No |
| **Milestone** | Issues | Always within one repo | Hypothesis / AC | No |
| **Project** | Milestones | May span multiple repos | Value proposition | Yes (T/I/OE) |
| **Portfolio** | Projects | Not tied to any repo | Strategic objective | Yes (T/I/OE) |

### 1.2 Structural Rules

- An issue belongs to exactly one milestone.
- A milestone belongs to exactly one project and lives in exactly one repo.
- A project may span multiple repos (its milestones are distributed across them).
- A repo may participate in multiple projects simultaneously. The milestone is the join point — each milestone belongs to one project, lives in one repo.
- A portfolio contains one or more projects. Portfolios may be nested (a portfolio can be a project in a larger portfolio).
- Repos are storage infrastructure, not organizational boundaries.

### 1.3 Same Primitives at Every Level (Conceptual Model)

Each level above issue has: dependency DAG, buffer, pipeline (crochet), actors, throughput accounting definitions. The fractal is a **conceptual model** — the same operations (triage, execute, review, rebalance) apply at every level, but each level has behavioral differences (e.g., triggers are discrete at bottom levels, continuous at top; TA applies at project/portfolio but not issue/milestone). Implementation uses **level-specific packages** with shared conventions (ref storage, YAML frontmatter, CLI patterns), not a generic abstraction layer. Each level gets its own package (as `issue/` and `milestone/` already do).

## 2. Crochet Pipeline as Triage

### 2.1 Core Insight

The crochet pipeline at level N serves dual purpose:
1. **Execution process** for work at level N.
2. **Triage gate** for work entering level N-1.

Concretely:
- Portfolio brainstorm+pushback triages which projects enter the system.
- Project brainstorm+pushback triages which milestones get planned.
- Milestone brainstorm+pushback triages which issues get refined.
- Issue brainstorm+pushback triages which implementation approach gets executed.

No separate triage stage is needed. The fractal structure itself provides triage.

### 2.2 Pipeline Stages as Hypothesis Tests

Each stage tests a hypothesis:

| Stage | Hypothesis |
|---|---|
| Brainstorm | "This problem is worth solving" |
| Pushback | "This spec is sound" |
| Refinement | "This decomposes into these issues" |
| Execution | "This code satisfies the acceptance criteria" |
| Postmortem | "This process worked and here's what we learned" |

Each stage either confirms (advance) or falsifies (loop back). The pipeline is a series of experiments, not a conveyor belt.

### 2.3 Postmortem Feeds Forward

Both `crochet:brainstorm` and `crochet:postmortem` produce **markdown reports** as their output. The postmortem report includes structured sections:
- **Questions answered**: what hypotheses were confirmed/refuted.
- **Questions raised**: what new questions emerged during execution.
- **Throughput classification**: was this milestone throughput (advanced the goal), waste, or learning?

This report is the **required input** for the next brainstorm at the same level. Brainstorm reads the previous postmortem markdown as input context, starting from "here's what we learned last time" not from a blank slate. This is how milestones chain: each one's results define what the next one should test. The data contract between the skills is the markdown report format — no special schema beyond identifiable sections.

### 2.4 Pipeline Changes Required

| Skill | Change |
|---|---|
| **crochet:onboard** | Extended: establish TA definitions (T/I/OE) at project kickoff. Required before first milestone. Guided conversation to nail down concrete, measurable definitions for all three measures. |
| **crochet:postmortem** | Extended: include throughput accounting. Output "questions answered" and "questions raised" that seed next brainstorm. Classify milestone result as throughput vs waste vs learning. |
| **crochet:brainstorm** | Modified: accepts postmortem output as input. Starts from prior learnings and raised questions. |
| **Project review** (new) | Periodic pull of drift detection, attention allocation, T/I/OE trends across milestones. Cadence-driven (tied to milestone completions and/or regular schedule). The ZTD weekly review applied to the project level. |

### 2.5 Data Surfacing

All signals are pull-based, triggered at natural SDLC checkpoints:

| Checkpoint | Data Pulled |
|---|---|
| Issue completion | Issue-level metrics (difficulty vs prediction, path overlap accuracy) |
| Milestone postmortem | Milestone TA (T/I/OE), hypothesis confirmed/refuted, learnings |
| Milestone kickoff | Previous postmortem learnings, buffer status, project-level T/I/OE trend |
| Project review (periodic) | Drift detection, attention allocation, rebalancing data across milestones |
| Portfolio review (periodic) | Cross-project throughput comparison, rebalancing signals |

No push notifications or daemons. The pipeline's natural cadence surfaces signals at the right time.

## 3. Throughput Accounting

### 3.1 The Three Measures (per Goldratt)

Defined at project and portfolio level during kickoff/onboard. Uses a **hybrid schema** where each measure has the appropriate level of structure:

- **Throughput (T)**: rate at which the system produces goal-units. Only work that advances the stated goal counts. Milestones that shipped but didn't advance the goal are waste, not throughput. Definition is project-specific (e.g., "milestones where fitness assessment passes and capability is used in next cycle"). **Schema**: a `ThroughputDefinition` string written at onboard (defines what counts as T for this project), plus a per-milestone `Classification` enum (`throughput`, `waste`, `learning`) recorded at postmortem. The system counts classifications over time for drift detection.
- **Inventory (I)**: work in the system that hasn't converted to throughput. **Fully computable** from existing git-zhi data: open/in-progress issues, incomplete milestones, specs in pipeline stages. No new schema needed — derived at query time. Inventory growing without throughput growing is a drift signal.
- **Operating Expense (OE)**: cost of keeping the pipeline running regardless of throughput. Agent compute, human attention spent on coordination/review/triage, pipeline overhead (postmortems, alignment checks, process maintenance). **Schema**: free-form text. Hardest to measure; structured fields added later when patterns emerge from real use.

### 3.2 Drift Detection

The system detects drift by observing relationships between T, I, and OE over time:

| Pattern | Signal |
|---|---|
| T flat + I growing | Constraint somewhere — work entering but not completing |
| T flat + OE growing | Process bloat — overhead consuming capacity without producing value |
| T declining + I declining | Pipeline starved — triage at level above has stalled |
| Completed milestones not converging on goal | Goal drift or wrong milestones being prioritized |

Drift detection is surfaced at project review checkpoints. The system prompts: "N milestones completed since last review. Here's what each postmortem said we learned. Here's the project goal. Are we making progress?" The human makes the throughput judgment.

When drift is detected, the system should surface: "It doesn't look like we're making progress toward [stated goal]. Either the goal has drifted or we're off course." This triggers The Choice's thinking processes — current reality tree to find the constraint, evaluate whether to update the goal or change course.

### 3.3 TA Definitions Are Living Documents

TA definitions are reviewed at the same cadence as the throughput accounting itself. The measures might be wrong — defining throughput as "milestones completed" then realizing completed milestones aren't producing value means the throughput definition drifted from reality. The review process must include "are our measures still measuring the right things?"

## 4. The Human as Drum

### 4.1 Core Principle

The human is the system's constraint (drum). The entire system subordinates to maximizing **human effectiveness** — not throughput of activity. "Cranking out 100 bad widgets is worse than cranking out 1 good one." Throughput is throughput of *value*, not *activity*.

### 4.2 Implications

- **Quality gates before the drum, not after.** Agentic review, test suites, alignment checks happen before work reaches human review. The human should only see work that's passed machine-verifiable quality bars.
- **Right-sized decisions.** Don't ask the human to review 500 lines — ask them to approve a design, then let agents execute. Crochet pipeline already does this: pushback/refinement are small decisions with high leverage; execution is large effort with low decision load.
- **WIP limits at the "awaiting human" stage.** If N things are waiting for review, don't release more work. Have agents do preparatory work that doesn't need human attention yet.
- **Drum's role changes by level.** At issue/milestone level: pacing execution. At project/portfolio level: strategic rebalancing decisions — less frequent, higher leverage, triggered by signals rather than completion events.

## 5. Trigger Mechanisms

### 5.1 Discrete (Bottom Levels)

- **Issue level**: issue completes → next ready issue pulls from the backlog (which was triaged by milestone-level brainstorm+pushback).
- **Milestone level**: milestone completes → postmortem → learnings feed next brainstorm → next ready milestone pulls from roadmap (which was triaged by project-level brainstorm+pushback).

### 5.2 Continuous (Upper Levels)

Projects and portfolios don't "complete and trigger the next one." They rebalance.

- **Project level**: milestone completes or conditions change → rebalance. "Given what we learned, is the next planned milestone still the right one? Should we re-triage?"
- **Portfolio level**: project hits inflection point or external conditions change → rebalance. "Are we investing attention in the right projects? Should we shift?"

The trigger is **throughput accounting against a stated goal** (The Choice), informed by:
- Postmortem learnings bubbling up from below
- Buffer health warnings (defensive signal)
- Attention allocation data (LifeBalance-style tracking)
- External events (market shifts, team changes, dependency changes)

The cadence combines event-driven signals (milestone completion, failed quality gates) with periodic review (ZTD weekly review pattern). The SDLC has natural checkpoints where reviews happen.

## 6. Actors

### 6.1 Persistent vs Ephemeral

| Type | Examples | Identity | WIP Limit | Throughput Tracked | Appears in TA |
|---|---|---|---|---|---|
| **Persistent** | Humans, agent teams/sessions | Yes | Yes (WIP=1 per level) | Yes | Yes |
| **Ephemeral** | Subagents | No | N/A (always 1:1) | No | No |

Ephemeral actors are invisible to git-zhi. They're internal implementation details of how a persistent actor does its work. A persistent actor picking up an issue might use 5 subagents internally — git-zhi sees one actor completing one issue.

### 6.2 WIP=1 per Persistent Actor per Level

One persistent actor owns one work item at a given level. "Owns" means responsible for throughput, not "is the only one touching it."

- A milestone owner orchestrates many issue workers within that milestone.
- A project owner orchestrates many milestone owners within that project.
- Ownership implies responsibility for throughput at that level.

### 6.3 Actors Are Orthogonal to Hierarchy

Teams and actors are a resource allocated to work, not a structural element bound to a hierarchy level. One or more teams might work on one or more projects/portfolios. The allocation is a function of where the drum decides attention should go, informed by throughput accounting.

### 6.4 Actor Type Doesn't Change the Model

The system works identically for human and agent actors. A persistent actor is a persistent actor. The only places where human vs agent matters:

- **Drum identification**: humans are always potential drums (scarce attention). Agents are not (elastic compute).
- **WIP enforcement semantics**: humans need protection from overload (effectiveness). Agents need different limits (diminishing returns on parallelism).
- **Pipeline stage participation**: some stages require human judgment (triage, pushback). Others can be fully agent-driven (execution, mechanical review).

## 7. Agent Team Coordination

### 7.1 Team vs Subagent Decision

The responsible persistent actor (milestone lead, project lead) decides whether to use teams or subagents for the work below them. This is a context-dependent judgment call, not a formula. Factors include:

- Do workers need lateral communication? (team)
- Is the work exploratory with high uncertainty? (team)
- Are work items independent with clear AC? (subagents may suffice)
- Are work items tightly coupled or sharing files? (team)

The decision can change mid-milestone. Early in a milestone (high uncertainty, plan validation) teams may be needed. Late in a milestone (well-understood remaining work) subagents may suffice. Or vice versa. One size does not fit all.

### 7.2 Mapping to Claude Code Agent Teams

| git-zhi Level | Agent Teams Role | Coordination |
|---|---|---|
| Project lead | Team lead (or human) | Delegates milestones to teammates |
| Milestone lead | Teammate (from project team) | Delegates issues to subagents or spawns issue-level team |
| Issue worker | Teammate or subagent (milestone lead decides) | Uses subagents for SDLC steps |
| SDLC step | Subagent (always) | Ephemeral, reports back |

### 7.3 Claude Code Integration Points

- **Shared task list**: maps to git-zhi's ready set at whatever level the team operates.
- **`TeammateIdle` hook**: capacity signal — persistent actor freed up, can pull next work item.
- **`TaskCompleted` hook**: throughput signal — work item completed, feed into TA.
- **`ParallelAssignment()`**: existing path-overlap detection for coordinating concurrent issue work.
- **`graph.Head(actor)`**: existing per-worker HEAD resolution for persistent actors.

### 7.4 Current Limitations

- Claude Code agent teams: "no nested teams" — a teammate cannot spawn its own team. This means you can't simultaneously have project-level team coordination AND issue-level team coordination. This is an implementation constraint that may lift; the model supports nesting.
- Agent team sweet spot: 3-5 teammates per team (documented guidance).
- Subagent concurrency: bounded by API rate limits (account-tier specific) and local resources (test contention, git locks, worktree availability).

## 8. Data Model

### 8.1 Within a Repo (Existing + Extensions)

Issues and milestones remain in `refs/zhi/_/` within each repo. Extensions:

- **Milestone gains**: `project` field (which project this milestone belongs to).
- **Project entity** (new): stored in `refs/zhi/_/projects/<name>/`. Contains: name, goal statement, TA definitions (T/I/OE), created timestamp, state. Actor references use the existing `type:identifier` string format (same as `Issue.Assigned` and `Transition.Actor`).
- **Portfolio membership** (new): stored in `refs/zhi/_/portfolio/`. Contains: portfolio name, project's role in portfolio.

#### Relationship to Existing `internal/project/` Package

The existing `internal/project/` package provides a **YAML-file-based** cross-repo aggregation tool (`project show <file>`, `project next --actor <name> <file>`). This reads a `ProjectDef` YAML file from disk — it is not backed by git refs.

The new ref-backed project entity is a different concept: a lifecycle-managed domain object with goal, TA definitions, and milestone ownership. During Phase 1a, **new CLI subcommands** (`project create`, `project review`, etc.) are added alongside the existing file-based commands. Both coexist under the `project` command tree without conflict.

In Phase 3 (cross-repo), the two concepts are **reconciled**: the YAML-file-based aggregation becomes a view/export of ref-backed state, or an import source for bootstrapping. The existing `ProjectDef` fields (repos, workers, feeds) inform the cross-repo sync design.

### 8.2 Cross-Repo Sync

Projects spanning multiple repos and portfolios spanning multiple projects require cross-repo data access.

**Approach**: distributed with convention (CRDT-like). Portfolio and project data is stored in every member repo and synced via a mechanism analogous to git remotes.

- Portfolio/project data lives in `refs/zhi/_/` in each member repo.
- Sync mechanism pushes/fetches this data between member repos.
- Conflicts resolve automatically — throughput events are append-only (milestone completed at time T with result X), naturally CRDT-compatible.
- Each repo is a remote for portfolio/project data to its peers.
- Pattern is inspired by the existing `git zhi sync` concept but is **novel infrastructure** — the Jira sync is hub-and-spoke via REST API, not peer-to-peer git-ref sync. See Phase 3 note below.

**Data that syncs**:
- Portfolio/project TA definitions
- Portfolio/project goal statements
- Membership (which repos/milestones belong to which projects/portfolios)
- Aggregated throughput data (or enough raw data to compute locally)
- Rebalancing decisions and history

### 8.3 Milestone-to-Project Linkage

The milestone is the join point between repos and projects:
- Each milestone has a `project` field referencing its parent project.
- A project entity lists its member milestones (name + repo reference).
- Querying "all milestones for project X" requires checking each member repo.

## 9. Theoretical Foundations

This spec draws on several established frameworks. They are not optional flavor — they are the design rationale.

| Framework | How It Applies |
|---|---|
| **Theory of Constraints (Goldratt)** | Identify the constraint (drum = human), subordinate everything to it, elevate only when necessary. The constraint moves — between agent capacity, user attention, pipeline stages, dependencies. |
| **Critical Chain Project Management** | Consolidate safety into buffers. Buffer consumption signals problems. The critical chain (longest dependency path) sets the pace at each level. |
| **Goldratt's Rules of Flow** | Portfolio-level WIP management. Don't release new work until the constraint has capacity. Triage before entry. |
| **The Choice (Goldratt)** | Scientific thinking: "here's the hypothesis and evidence we should test next." Every gap in understanding is a testable hypothesis. Milestones are experiments. Acceptance criteria at milestone and project level ARE the hypotheses. |
| **Throughput Accounting** | T/I/OE as the three measures. Only throughput toward the goal counts. Cost accounting (tracking allocation) is insufficient — must track value conversion. |
| **Zen to Done (Babauta)** | MITs (most important things) map to the ready set. Regular cadence (weekly review) for upper-level rebalancing. Habit over system — tooling must be simple enough to maintain. |
| **LifeBalance (Llamagraphics)** | Hierarchical goals with attention tracking. System surfaces where attention is going vs where it should go. Rebalancing trigger is attention drift, not completion. |

## 10. Implementation Phasing

This spec describes a large system. Implementation should be incremental, with each phase delivering usable value.

### Phase 0: Foundation (prerequisite)
- git-zhi issues and milestones work as-is (done).
- Crochet pipeline works for single-repo, single-project workflows (done).

### Phase 1a: Project Entity + Milestone Linkage
- Add project entity to `refs/zhi/_/projects/<name>/` with: name, goal statement, created timestamp, state, owner (actor string).
- Add `project` field to milestone struct (backward-compatible: empty string for unlinked milestones).
- Add CLI commands: `git zhi project create`, `git zhi project list`, `git zhi project show <name>` (ref-backed, distinct from existing file-based `project show <file>`).
- Add `git zhi milestone edit --project <name>` to link milestones to projects.
- Project entity lists its member milestones (queried from milestone refs in the same repo).
- **Immediate value**: single-repo project lifecycle with milestone grouping.

### Phase 1b: Throughput Accounting Framework
- Add TA definitions to project entity: `ThroughputDefinition` (string), `OperatingExpenseNotes` (free-form string). Inventory is computed from existing data at query time.
- Add `Classification` field to milestone postmortem data: `throughput`, `waste`, or `learning` (recorded when milestone completes).
- Add `git zhi project review` command: surfaces T/I/OE summary, milestone classifications, and goal statement for human judgment.
- **Immediate value**: throughput accounting at project level, milestone classification at completion.

### Phase 1c: Crochet Skill Extensions
- Extend `crochet:onboard` to establish TA definitions (throughput definition, OE notes) at project kickoff via guided conversation.
- Extend `crochet:postmortem` to produce a markdown report with structured sections: "Questions Answered", "Questions Raised", "Throughput Classification" (throughput/waste/learning). This report format is the data contract for Phase 2.
- **Immediate value**: structured postmortem output, TA definitions captured at onboard.

### Phase 2: Postmortem-Feeds-Brainstorm
- Modify `crochet:brainstorm` to accept postmortem output as input.
- Milestone chains: each completion seeds the next brainstorm.
- Drift detection: surface patterns in T/I/OE at project review.
- **Immediate value**: hypothesis-driven milestone chaining, early drift warnings.

### Phase 3: Cross-Repo Projects (Exploratory — requires design spike)
- **Note**: Cross-repo peer-to-peer ref sync is novel infrastructure with no precedent in the codebase. The Jira sync model (hub-and-spoke via REST) does not transfer directly. This phase requires a design spike before implementation to resolve: member repo registration, ref push/fetch mechanics, conflict resolution for non-append-only data (goal edits, membership changes).
- Reconcile ref-backed project entity with existing `internal/project/` YAML-file-based aggregation. The YAML file becomes a view/export of ref state or an import source.
- Project entity sync across member repos.
- Milestone-to-project linkage across repos.
- Cross-repo throughput aggregation.
- **Immediate value**: multi-repo project management for real-world team use.

### Phase 4: Portfolio Entity (Depth-1 Only)
- Add portfolio entity with goal + TA definitions. **Depth-1 only**: a portfolio contains projects, but nested portfolios are deferred until a real use case demands the recursive traversal machinery. The model supports nesting; the implementation starts flat.
- Portfolio-level review skill (aggregates across projects).
- Attention allocation tracking and rebalancing signals.
- Portfolio data sync (CRDT-like across all member repos).
- Resolve Open Question #1 (portfolio bootstrap location) during this phase's design.
- **Immediate value**: portfolio management for a team across multiple projects.

### Phase 5: Agent Team Integration
- Agent teams as persistent actors with identity in git-zhi.
- `TeammateIdle` and `TaskCompleted` hooks feeding TA.
- Ready set surfacing for agent team task lists.
- Team-vs-subagent guidance surfaced from git-zhi data (path overlap, dependency coupling, uncertainty level).
- **Immediate value**: agentic team orchestration using git-zhi as coordination substrate.

## 11. Testing Strategy

### Unit Tests
- Project and portfolio entity CRUD (marshal/unmarshal, load/save, validate).
- TA definitions storage and retrieval.
- Milestone-to-project linkage.
- Drift detection pattern matching (T/I/OE trend analysis).
- Cross-repo sync conflict resolution.

### Integration Tests
- Project spanning multiple test repos with milestones in each.
- Postmortem output feeding brainstorm input.
- Project review skill pulling correct data from multiple milestones.
- Portfolio aggregation across multiple projects.
- Sync mechanism between repos (create, modify, sync, verify convergence).

### End-to-End Tests
- Full crochet pipeline cycle: onboard (establish TA) → brainstorm → pushback → refine → execute → postmortem → next brainstorm.
- Drift detection scenario: create project with goal, complete milestones that don't advance it, verify drift signal surfaces at review.
- Multi-repo project: milestones in different repos, project review aggregates correctly.
- Agent team integration: persistent actor identity, WIP enforcement, throughput tracking through team hooks.

### Validation Against Immediate Use Case
- One portfolio, multiple projects, multiple repos.
- 11 persistent actors (humans) with varying levels of work.
- Throughput accounting surfaces meaningful data at project review.
- Drift detection catches projects not converging on goals.
- Rebalancing signals inform attention allocation decisions.
