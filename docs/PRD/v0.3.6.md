# v0.3.6 PRD — Milestone Reopen, Orphaned Dependency Warnings, and GitHub Issues Import

## Overview

v0.3.6 addresses three gaps identified during the v0.3.2–v0.3.5 fitness
assessment series:

1. **Milestone reopen:** Completed milestones cannot be reopened. This blocked
   the crochet:execute loop when post-completion work was needed (observed
   during v0.3.5 when fixes were added after milestone completion).

2. **Orphaned dependency warnings:** `--purge` silently cleans up dependency
   edges. If an issue is referenced by other issues' `blocks`/`blocked_by`
   lists, the user should be warned before deletion.

3. **GitHub Issues import:** A `crochet:import` subskill that uses `gh` CLI
   and the GitHub REST API to import GitHub milestones, issues, and native
   dependency relationships into git-zhi chains.

## Problem Statement

### Completed milestones are a one-way door

Once a milestone transitions to "completed," there is no way to reopen it.
The only workaround is to create a new milestone. During v0.3.5, fixes
identified in the postmortem had to be added to a new milestone rather than
reopening the existing one. This is friction that breaks the natural
"reopen and continue" workflow.

### Purge silently removes dependency edges

`git zhi issue edit <ref> --purge --yes` removes all `blocks` and
`blocked_by` references from upstream and downstream issues. This is correct
behavior, but the user gets no warning about which issues will be affected.
If you purge an issue that's a critical dependency for 5 other issues, you
only find out after the fact.

### No path from GitHub Issues to git-zhi

Teams using GitHub Issues have no way to import their existing issue
structure into git-zhi. The jira sync plugin provides this for Jira, but
GitHub Issues users must manually recreate all issues, losing dependency
relationships and metadata.

## Changes

### 1. Milestone Reopen

**CLI change:** `git zhi milestone edit <name> --state reopen`

**Behavior:**
- Transitions milestone state from "completed" to "open"
- Clears the `Completed` timestamp
- No quality gates on reopen (gates are only enforced on completion)

**State machine:** The milestone state machine gains one new transition:

```
open → completed  (via --state complete, with quality gates)
completed → open  (via --state reopen, no gates)
```

**Implementation:** In `runMilestoneEdit`, extend the `--state` handler to
accept "reopen" in addition to "complete". When the action is "reopen":
1. Verify the milestone is currently in "completed" state
2. Set `ms.State = "open"`
3. Set `ms.Completed = nil`
4. Persist the milestone
5. Output: `<name>: state → open (reopened)`

No issue state changes. Issues in the milestone retain their current state
(done, cancelled, etc.). New issues can be added to the reopened milestone
normally.

### 2. Orphaned Dependency Warning on Purge

**CLI change:** No new flags. Behavioral change to `--purge`.

**Current behavior:** `--purge --yes` deletes the issue and silently cleans
up all dependency edges in upstream/downstream issues.

**New behavior:** Before deleting, `--purge --yes` reports which issues
will be affected:

```
Purging 019d0891 "Fix widget alignment"

Dependency cleanup:
  019a1234 "Build widget framework" — will remove from blocks list
  019b5678 "Polish widget styles" — will remove from blocked_by list

Purged 019d0891
```

If `--purge` is used without `--yes` and there are dependents, the error
message should mention the affected count:

```
--purge requires --yes flag for confirmation (2 dependent issues will be updated)
```

**Implementation:** Before the existing cleanup loop in `runIssueEditPurge`:
1. Count upstream (`BlockedBy`) and downstream (`Blocks`) references
2. If `--yes` is not set and there are dependents, include the count in the
   error message
3. If `--yes` is set, print a summary of affected issues before performing
   the cleanup (using existing logic unchanged)

The cleanup logic itself does not change — only the reporting.

### 3. GitHub Issues Import Skill

A new `crochet:import` subskill at
`skills/import/github.md` that imports GitHub Issues into git-zhi.

**Trigger:** User says "import from GitHub," "import GitHub milestone," or
runs `crochet:import --source github`.

**Process:**

#### Step 1: Identify Source

Accept one of:
- A GitHub milestone name: `--milestone "v2.0"`
- A GitHub label: `--label "sprint-23"`
- A list of issue numbers: `--issues "1,2,3"`
- No filter (all open issues)

The skill uses `gh` CLI for all GitHub interaction.

#### Step 2: Fetch Issues

```bash
gh issue list --milestone "v2.0" --state all --json number,title,body,state,labels,milestone,assignees --limit 0
```

Parse the JSON output. The `--limit 0` fetches all matching issues without
an arbitrary cap. If the result set is very large, warn the user with the
count before proceeding.

#### Step 3: Fetch Dependencies

For each issue, fetch native GitHub dependency data via the REST API.
The dependency endpoints require a versioned API header (GA August 2025):

```bash
gh api -H "X-GitHub-Api-Version: 2026-03-10" repos/{owner}/{repo}/issues/{number}/dependencies/blocked_by
gh api -H "X-GitHub-Api-Version: 2026-03-10" repos/{owner}/{repo}/issues/{number}/dependencies/blocking
```

Build a dependency graph from the responses. Only intra-repo dependencies
are imported; cross-repo dependency edges are skipped with a warning
(GitHub supports cross-repo blocking, but the mapping file is scoped to
a single repo).

#### Step 4: Map Fields

| GitHub Field | Zhi Field | Mapping |
|---|---|---|
| `title` | `title` | Direct |
| `body` | `body` | Direct |
| `state` (open) | `state` | → `pending` |
| `state` (closed) | `state` | → `done` |
| `labels[].name` | `labels` | Direct (array) |
| `milestone.title` | `milestone` | Direct (create zhi milestone if it doesn't exist) |
| `assignees[0].login` | `assigned` | → `human:<login>` |
| `number` | `tracker_id` | → `github:<owner>/<repo>#<number>` |
| `blocked_by` deps | `blocked_by` | Map via issue number → zhi UUID lookup |
| `blocking` deps | `blocks` | Map via issue number → zhi UUID lookup |

The `tracker_id` field follows the existing convention (`jira:LOPS-142`)
and provides a secondary idempotency check independent of the mapping
file. It also enables future bidi sync to identify which zhi issues
originated from GitHub.

#### Step 5: Check Mapping File

Load `.git/zhi-sync/ghi-mapping.json` if it exists. Structure:

```json
{
  "repo": "owner/repo",
  "issues": {
    "42": "019d0891-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
    "43": "019d0892-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
  }
}
```

Skip any GitHub issue number already present in the mapping (idempotent
re-run). New issues are appended to the mapping after creation.

#### Step 6: Create Milestone (if needed)

If the GitHub milestone maps to a zhi milestone that doesn't exist:

```bash
git zhi milestone add "<milestone name>"
```

If the GitHub milestone has a due date, set it:

```bash
git zhi milestone edit "<milestone name>" --due <YYYY-MM-DD>
```

#### Step 7: Present for Review

Show the proposed import to the user, following the existing
`crochet:import` pattern:

```
Import from github.com/owner/repo milestone "v2.0":

  #42  "Fix login timeout"         → pending, milestone: v2.0
  #43  "Add password reset"        → pending, milestone: v2.0, blocked_by: #42
  #44  "Update auth docs"          → done, milestone: v2.0, blocked_by: #43

  3 issues (2 new, 1 already imported)
  1 milestone (v2.0 — exists)
  2 dependency edges

  Accept? [y]es, [e]dit, [s]kip
```

#### Step 8: Create Issues (Two-Pass)

**Pass 1 — Create issues:** For each accepted issue, create it via
`git zhi issue add "<title>" --body "<body>" --milestone "<ms>"`. Capture
the newly created zhi UUID from the output and record it in the mapping
file keyed by GitHub issue number.

**Pass 2 — Wire dependencies:** For each dependency edge in the graph,
look up both the source and target zhi UUIDs from the mapping file, then
wire the edge:

- GitHub `blocked_by` (issue X is blocked by issue Y) →
  `git zhi issue edit <X-uuid> --after <Y-uuid>`
- GitHub `blocking` (issue X blocks issue Y) →
  `git zhi issue edit <X-uuid> --block <Y-uuid>`

If a dependency target is not in the mapping (not in the import set and
not previously imported), skip the edge with a warning.

#### Step 9: Update Mapping

Append new entries to `.git/zhi-sync/ghi-mapping.json` and write it back.

**Bidirectional sync (future):** The mapping file is designed to be expanded
with per-issue snapshot fields when three-way merge is needed. The current
single-file format is intentionally simple — it stores only the identity
mapping. When bidi sync is added, each entry can grow to include last-synced
field values without changing the file location or top-level structure.

## Design Principles

1. **Reopen is the inverse of complete.** Clearing the completed timestamp
   and setting state to open is the minimal correct behavior.
2. **Warn before destructive actions.** Purge already requires `--yes`;
   adding a dependency report makes the confirmation meaningful.
3. **`gh` CLI is the interface to GitHub.** No Go code for GitHub API
   interaction — the skill shells out to `gh` and `gh api`.
4. **Idempotent import.** Re-running the import on the same milestone skips
   already-imported issues. The mapping file is the source of truth for
   what's been imported.
5. **Single mapping file.** `.git/zhi-sync/ghi-mapping.json` stores
   issue number → UUID mappings. Expand to per-issue snapshots when bidi
   sync is needed.

## Test Strategy

TDD in Go. Real on-disk git repos via `t.TempDir()`. No mocks.

### Milestone Reopen Tests

- Reopen a completed milestone: state transitions to "open", Completed
  timestamp is cleared
- Reopen an already-open milestone: error ("cannot reopen: milestone is
  open, expected completed")
- Issues in the milestone retain their state after reopen
- Complete → reopen → complete round-trip works (quality gates re-enforced
  on second completion)

### Orphaned Dependency Warning Tests

- Purge an issue with no dependents: output unchanged (no "Dependency
  cleanup" section)
- Purge an issue with upstream and downstream dependents: output lists
  affected issues before "Purged" line
- Purge without --yes when dependents exist: error message includes
  both "--yes" and the dependent count (e.g., "2 dependent issues")
- Purge without --yes when no dependents: error message unchanged (just
  "--purge requires --yes", no count)
- Existing cleanup behavior is preserved: dependency edges are still
  removed correctly

### GitHub Issues Import Tests

The import is a crochet skill (markdown), not Go code. Testing is
behavioral:

- Import a GitHub milestone with 3 issues: all 3 created in zhi with
  correct fields
- Import with dependencies: `blocks`/`blocked_by` edges are wired correctly
- Re-run import on same milestone: already-imported issues are skipped,
  new issues are added
- Import creates zhi milestone if it doesn't exist
- Mapping file is created on first import, updated on subsequent imports
- Import with no matching issues: reports "0 issues to import" and exits
  cleanly

## Non-Goals

- Bidirectional sync (push zhi state back to GitHub Issues)
- Three-way conflict detection for GitHub Issues
- GitHub Projects integration (only Issues and Milestones)
- GitHub sub-issues import (only blocking/blocked-by dependencies)
- Cross-repo dependency import (only intra-repo blocking/blocked-by edges)
- Go code for GitHub API interaction (skill uses `gh` CLI)

## Known Gaps

- **Completed milestones accept new issues without reopen.** `issue add
  --milestone <completed-ms>` succeeds — there is no gate checking milestone
  state during issue creation. The reopen feature makes this less likely to
  be a problem in practice (users will reopen first), but the gap exists.
  Out of scope for v0.3.6; consider for a future release.

## Error Handling

### Milestone Reopen
- Milestone not found: standard "milestone not found" error
- Milestone not completed: "cannot reopen: milestone is <state>, expected
  completed"

### Orphaned Dependency Warning
- No new error paths. Warning is informational only.

### GitHub Issues Import
- `gh` not installed: "gh CLI not found — install from https://cli.github.com"
- `gh` not authenticated: "gh auth status failed — run 'gh auth login' first"
- GitHub API rate limit: report the error from `gh api` and suggest retry
- Issue number in mapping but no longer exists on GitHub: skip with warning
- Dependency target not in import set and not in mapping: warn and skip
  the dependency edge (don't fail the whole import)
