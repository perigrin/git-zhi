# v0.3.x Fitness Assessment

## Purpose

This project stress-tests the v0.3.x git-zhi release line in real-world
conditions and improves it as deficiencies surface. The vehicle is the
`perl-development` Claude Code plugin — a non-trivial deliverable with a
real PRD, real validation targets, and real complexity. The plugin is the
means; a better v0.3.x is the goal.

**What we are testing and improving:**

|Component               |What we want to know                                                              |
|------------------------|----------------------------------------------------------------------------------|
|`git-zhi-historian`     |Does brownfield onboarding work on real repos? What history shapes cause problems?|
|`crochet:refinement`    |Does PRD → chain produce a workable, correctly-sized issue set?                   |
|`crochet:pushback`      |Does pre-flight validation catch real problems in a real PRD?                     |
|`crochet:alignment`     |Does post-phase validation catch real drift? Does it over- or under-fire?         |
|`crochet:assess`        |Does codebase gap analysis produce actionable output?                             |
|`crochet:onboard`       |Does onboarding scaffold correctly for a new project?                             |
|`crochet:postmortem`    |Does the retrospective surface real learnings?                                    |
|Superpowers / Ralph Loop|Does autonomous execution sustain across multi-issue milestones?                  |
|Episodic memory         |Does cross-session continuity hold? Does retrieval actually help?                 |
|Sanbao / telemetry      |Are the telemetry signals meaningful for an agentic workflow?                     |

**What we ship:**

A shippable `perl-development` v0.1.0 plugin and a meaningfully better
v0.3.x stack. Both happen in parallel — the plugin build is the pressure
that reveals what needs fixing, and the fixes happen immediately rather
than in a separate polish sprint.

**What we produce:**

1. The plugin itself
1. Inline improvements to git-zhi, crochet, and related tools as friction
   surfaces
1. A fitness report per v0.3.x component reflecting its state *after* fixes
1. A residual polish backlog for items not resolved in-flight
1. A set of v0.4 callouts where a v0.4 feature would have materially changed
   what was possible

## Observation and Fix Protocol

Every issue in this project carries a standard observation footer:

```
## Observations
- Component: <which v0.3.x component was exercised>
- Verdict: WORKS / ROUGH / BLOCKED / NOT_EXERCISED
- Notes: <what happened; friction points; unexpected behavior>
- Fix applied: <what was changed inline, if anything>
- Follow-on issue: <issue ID if a fix issue was spawned, or "none">
- v0.4 callout: <v0.4 feature that would have helped, if any>
```

v0.4 callouts are discovery, not confirmation. Note any moment where a
feature that does not exist in v0.3.x would have materially changed the
outcome, even if it is not on any roadmap.

Verdict definitions:

- **WORKS** — component performed as designed with no material friction
- **ROUGH** — component worked but with friction; a fix was applied or
  a follow-on issue was spawned
- **BLOCKED** — component could not complete its function; fix required
  before proceeding
- **NOT_EXERCISED** — issue completed without triggering the component
  meaningfully

### Inline Fix Protocol

When a verdict is ROUGH or BLOCKED:

1. **Assess fix scope** — is this a one-line correction, a skill update,
   or a deeper change to git-zhi or crochet?
1. **Apply small fixes immediately** — if the fix is self-contained (a
   skill clarification, an AC rewrite, a CONTRIBUTING.md addition), apply
   it in the same session before proceeding. Record in `Fix applied`.
1. **Spawn a follow-on issue for larger fixes** — if the fix requires
   a separate focused session, `git zhi issue add` a new issue immediately,
   blocking the current milestone's resolution issue or unblocked if it
   can run in parallel. Record the issue ID in `Follow-on issue`.
1. **Never work around a BLOCKED verdict** — if a component cannot perform
   its function, fix it or explicitly defer it with a documented rationale.
   Substituting manual work and marking it done defeats the purpose.
1. **Label fix issues** — all follow-on fix issues get labeled `v0.3x-polish`
   so they're filterable: `git zhi issue list --label v0.3x-polish`.

The milestone resolution command does not fire until all `v0.3x-polish`
issues spawned within that milestone are also resolved.

## Milestones

### Milestone 0: Stack Bootstrap

**Component under test:** `crochet:onboard`, `crochet:pushback`, episodic memory

**Goal:** Get the full v0.3.x stack operational. Surface first friction
points before any real work begins. Apply fixes immediately.

**Resolution:** All tools verified; pushback findings addressed or
documented; episodic memory returning relevant results. All
`v0.3x-polish` issues spawned here are resolved.

**Issues:**

- Install and verify: git-zhi, crochet, superpowers, episodic-memory
- Run `crochet:onboard` — observe whether it handles a meta-project
  (a project whose output is a Claude Code plugin) without confusion
- Configure episodic-memory — verify sync, test search against prior
  conversations about the plugin design, observe retrieval quality
- Run `crochet:pushback` against `docs/PRD/pvm-plugin-prd.md` — record
  all findings; apply fixes or document as accepted
- Spawn fix issues for any ROUGH/BLOCKED verdicts

**What we're watching:**

- Does `crochet:onboard` scaffold correctly for a non-application project?
  Does CONTRIBUTING.md reflect the right context?
- Does `crochet:pushback` find real issues, or produce generic observations?
  Is the signal-to-noise ratio acceptable?
- Does episodic memory semantic search surface relevant prior conversations?
  Is retrieval fast enough to use in a session opening?

### Milestone 1: Historian on Real Repos

**Component under test:** `git-zhi-historian`, `crochet:assess`

**Goal:** Run historian on all four validation repositories. Fix historian
deficiencies as they surface. Document what the tool can and cannot do
against real commit histories.

**Resolution:** All four repos have zhi chains; `crochet:assess` reports
exist for each; historian fitness document written; all `v0.3x-polish`
issues from this milestone resolved.

**Issues:**

- Run historian on **Chalk** (bootstrap branch)
- Run historian on **Iterum**
- Run historian on **Blawd**
- Run historian on **Registry**
- Run `crochet:assess` on each repo post-historian
- Write `docs/fitness/historian.md`
- Spawn fix issues for any ROUGH/BLOCKED verdicts on historian or assess

**What we're watching:**

- How does historian handle repos without ticket references in commits?
  (Blawd is the stress case here)
- Do confidence scores reflect actual quality? Are they calibrated?
- Does the resulting chain provide enough context for the Ralph Loop?
  Or does it need cleanup before execution?
- Does `crochet:assess` output actually help plan the plugin work, or is
  it too abstract to be actionable?

**Expected fix territory:** Confidence scoring calibration; handling of
Dist::Zilla-style changelogs; `crochet:assess` output specificity.

**v0.4 callout:** `git-zhi-anthropologist` would provide cluster analysis
that historian can't — note specifically what that would have revealed for
each repo.

### Milestone 2: PRD to Chain

**Component under test:** `crochet:refinement`, `crochet:alignment`

**Goal:** Decompose the plugin PRD into an executable zhi chain. Fix
refinement and alignment deficiencies as they surface. Document how much
human correction the chain required.

**Resolution:** `make validate-chain` passes; alignment report exists
with all HIGH findings resolved; delta between chain-as-produced and
chain-as-corrected is documented. All `v0.3x-polish` issues resolved.

**Issues:**

- Run `crochet:refinement` on `docs/PRD/pvm-plugin-prd.md`
- Inspect the chain before correction — record observations on scope,
  issue sizing, and dependency structure as-produced
- Run `crochet:alignment` — record all findings by severity
- Apply HIGH findings; document MEDIUM as accepted delta; log LOW
- Measure and record correction delta: how many issues were resized,
  renamed, re-dependencied, or added/removed?
- Write `make validate-chain` script
- Write `docs/fitness/refinement.md`
- Spawn fix issues for ROUGH/BLOCKED verdicts

**What we're watching:**

- Does refinement produce session-sized issues or does it over/under-decompose?
- Does it correctly identify the skill-per-issue structure?
- Does alignment catch real drift or produce false positives?
- What percentage of the chain needed human correction post-refinement?
  This number is the key fitness signal for refinement quality.

**Expected fix territory:** Issue sizing heuristics for plugin/skill
deliverables (different from software features); alignment sensitivity
tuning.

### Milestone 3: Version Detection and Toolchain Infrastructure

**Component under test:** Superpowers / Ralph Loop (first sustained run), episodic memory

**Resolution:** `perl:detect-version`, `perl:require-toolchain`,

- `write-perl.md` command dispatcher — version detection + skill routing
- Validation against Chalk (5.42) and Blawd (older Perl) to verify dispatch
- Spawn fix issues for ROUGH/BLOCKED verdicts

**Episodic memory protocol — every session in this milestone and all subsequent milestones:**

Before reading the current issue:

```
episodic-memory search "<current issue title>"
episodic-memory search "perl writing skills v0.3 fitness"
```

Record in the session's first commit: what was retrieved, whether it
was useful, and whether it changed any decisions. This data feeds
`docs/fitness/episodic-memory.md`.

**What we're watching (Ralph Loop):**

- Does the loop sustain without human re-steering? Record every
  intervention: what caused it and what fixed it.
- Does the structured context block give agents enough to proceed?
  Where did agents need to do archaeology despite the context block?
- Where does the loop stall, and is the stall due to zhi, crochet, the
  skill being built, or the validation repo?

**Expected fix territory:** Loop stall patterns; context block completeness
heuristics.

## What Counts as "Done"

This project is done when:

1. **The fitness report is honest and post-fix.** Verdicts reflect component
   state *after* inline fixes, not before. Residual issues are specific,
   not generic.
1. **The plugin passes `make validate-plugin`** for all four repos.
1. **PAAD was actually exercised.** At least one alignment finding
   materially changed the output. If it never fired, that is a finding.
1. **Episodic memory continuity is documented.** We have specific examples
   of retrieval helping or not helping, not a general impression.
1. **The v0.3x-polish label is resolved.** All follow-on fix issues have been
   completed. No `v0.3x-polish` issues remain open at project close.
1. **The residual backlog is honest.** Items that were not fixed have
   explicit rationale — not "we ran out of time" but "this requires a
   design change that is out of scope for v0.3.x."

-----

## What This Project Is Not

- **A workaround project.** BLOCKED verdicts get fixes, not substitutions.
- **A separate polish sprint.** The polish happens here, inline, as the
  deficiency is encountered — not in a follow-up project.
- **A v0.4 project.** v0.4 features are observed and noted, not built.
- **A Registry development project.** Registry is the next project,
  using this plugin and benefiting from the improved v0.3.x stack.

-----

## Relationship to Registry Development

Upon completion, Registry development begins as a new zhi project using
the full `perl-development` + improved v0.3.x stack. The telemetry
baseline and fitness report from this project inform how that project is
set up and monitored. The residual polish backlog informs whether v0.3.x
needs further work before Registry begins.
