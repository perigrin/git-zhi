## Critical Issues

### [C1] Missing milestone name validation allows git ref path traversal
- **File:** `internal/cli/milestone_add.go:32`, `internal/cli/milestone_edit.go:97`
- **Bug:** No `ValidateMilestoneName` function exists. Milestone names are used directly in ref paths (`milestone.RefPrefix + name`). A name containing `../` could write to unintended ref locations in the git namespace.
- **Impact:** Labels have explicit validation via `ValidateLabelName` (rejects `/`, `..`, `_`), but milestones have none. A user could accidentally or maliciously create refs outside the `refs/zhi/_/milestones/` namespace. The rename path (`--name`) has the same gap.
- **Suggested fix:** Add `ValidateMilestoneName` analogous to `ValidateLabelName`. Apply it in `runMilestoneAdd` and the `--name` rename path.
- **Confidence:** High
- **Found by:** Security
- **Note:** Pre-existing issue exposed by review, not introduced by this diff.

## Important Issues

### [I1] Purge does not clean up label index refs
- **File:** `internal/cli/issue_edit.go:1155-1167`
- **Bug:** Purge cleans up tag refs and dependency edges but not label index refs under `refs/zhi/_/labels/<label>/<uuid>`. A purged labeled issue leaves stale index entries that `LoadLabelIndex` will return, causing downstream `--label` filtering to reference a deleted issue.
- **Impact:** `reindex` fixes it, but stale entries persist until then. Other state transitions (done, cancel) don't clean up labels either, but purge is the only operation that permanently deletes the ref.
- **Suggested fix:** After the tag cleanup block, iterate `iss.Labels` and delete `refs/zhi/_/labels/<label>/<uuid>` for each.
- **Confidence:** High
- **Found by:** Logic & Correctness, Error Handling

### [I2] WriteEntity errors silently discarded during purge dependency cleanup
- **File:** `internal/cli/issue_edit.go:1130, 1151`
- **Bug:** `_ = app.Store.WriteEntity(...)` on both upstream and downstream cleanup. If a write fails, purge still deletes the target issue ref (line 1170), leaving a dangling dependency edge in the affected issue -- a graph referential integrity violation.
- **Impact:** Silent data corruption. The user sees "Purged" but the dependency graph is inconsistent.
- **Suggested fix:** Collect write errors and report them as warnings, or fail the purge before deleting the target ref if any cleanup write fails.
- **Confidence:** High
- **Found by:** Error Handling, Concurrency & State

### [I3] Blank state in reopen error message for default milestones
- **File:** `internal/cli/milestone_edit.go:266`, `internal/cli/milestone_edit_test.go:455`
- **Bug:** `EnsureInitialized` creates milestones with `State: ""` (Go zero value). When a user tries to reopen such a milestone, the error reads `"cannot reopen: milestone is , expected completed"` with a blank state name. The test comment incorrectly states the state is "open".
- **Impact:** Confusing UX. Users see a blank where a state name should be.
- **Suggested fix:** Either initialize milestone state to `"open"` in `EnsureInitialized`, or handle empty string in the error: `if ms.State == "" { state = "open" }`.
- **Confidence:** High
- **Found by:** Logic & Correctness, Error Handling

### [I4] Stored command injection via milestone resolution field
- **File:** `internal/cli/milestone_edit.go:177`
- **Bug:** The `Resolution` field from milestone YAML is passed directly to `exec.Command("sh", "-c", ms.Resolution)`. Anyone with push access to the repo can modify milestone refs to inject arbitrary shell commands that execute when another user runs `--resolve` or `--state complete`.
- **Impact:** In shared repos, this is a privilege escalation vector. By design (resolution is meant to be a command), but undocumented and has no confirmation prompt.
- **Suggested fix:** Display the resolution command and prompt for confirmation before execution, or document the security implications.
- **Confidence:** Medium
- **Found by:** Security
- **Note:** Pre-existing issue, not introduced by this diff.
